# Repository Guidelines

A collection of independent, Windows-only C#/WPF **live-memory trainers** for classic games — mostly DOS titles running under **DOSBox / DOSBox-X**, plus three native 32-bit Windows titles (`ImperialismIITrainer`, `BeachHead2000Trainer` and `Civilization3ConquestsTrainer`). Each trainer attaches to the running process (the emulator, or the game itself for the native target), signature-scans or value-scans its RAM to locate game state at runtime (addresses are never hard-coded), and reads/writes it live — with freeze toggles, "max" buttons, and, for some titles, offline save editing. Several also carry a reverse-engineering workspace behind their offsets.

## Project Structure & Module Organization

Nearly every top-level folder is a **self-contained trainer** with its own solution/project, `README.md`, a PowerShell run script (usually `Run.ps1`), and (mostly) its own `AGENTS.md` — read the per-project `AGENTS.md`/`README.md` before working inside one:

- `AirborneRangerTrainer/`, `AlternateRealityTrainer/`, `AmberstarTrainer/`, `AutoduelTrainer/`, `BardsTale1Trainer/`, `BattleTech1Trainer/`, `BeachHead2000Trainer/`, `Civilization3ConquestsTrainer/`, `ColonizationTrainer/`, `DarklandsTrainer/`, `DarkDesigns1Trainer/`, `DragonWarsTrainer/`, `EyeOfTheBeholder1Trainer/`, `HillsfarTrainer/`, `JumpmanLivesTrainer/`, `ImperialismIITrainer/`, `KeefTrainer/`, `LordsOfTheRealmTrainer/`, `MightAndMagic1Trainer/`, `MinesOfTitanTrainer/`, `MoriaTrainer/`, `PiratesTrainer/`, `PoolOfRadianceTrainer/`, `QuestForGlory1Trainer/`, `RailroadTycoonTrainer/`, `ShogunTrainer/`, `SwordOfAragonTrainer/`, `SwordOfTheSamuraiTrainer/`, `SyndicatePlusTrainer/`, `ThePerfectGeneral2Trainer/`, `WarOfTheLanceTrainer/`, `WastelandTrainer/`, `Wizardry1Trainer/`.

`WastelandTrainer/` (Wasteland — Interplay/EA, 1988) is a full trainer: `src/WastelandTrainer/` (`net8.0-windows`, references `GameTrainers.Common` for both `Memory` and `Mvvm`), a `test/FormatCheck/` harness, its own `.sln`/`Run.ps1`/`README.md`/`AGENTS.md`, and Party/Inventory/References/Maps tabs. It locates the party by **structure** (an array of seven contiguous 256-byte records that pack from slot 0) rather than by a static anchor, and teleports by writing the party X/Y in the party-state header that precedes the roster. Its captured RAM dumps (`*.bin`, `*.csv`, `memdump.md`) live under `.data/` (git-ignored by `.*/`) — never `git add` the multi-hundred-MB dumps.

Layout varies: some use a single `Trainer/` project (no `.sln`), others `src/<Name>/` with a `.sln` and a `test/FormatCheck/` harness. `MightAndMagic1Trainer` is the architectural template the others were ported from. Common layers: Win32 P/Invoke (`Native*.cs`), process/guest-memory access, a game-knowledge layer holding all reverse-engineered offsets as constants, and hand-rolled MVVM (`ObservableObject`/`RelayCommand`).

`GameTrainers.Common/` is a shared library that extracts the game-agnostic plumbing out of that duplication: `GameTrainers.Common.Memory` (process/guest-memory access — `ProcessMemory`/`MemoryRegion`, `NativeMethods`, `MemorySearcher`, `MemoryDumper`, `DumpComparer`, `BytePatternScanner`, `GlobalHotkeys`, `KeyboardSender`) and `GameTrainers.Common.Mvvm` (`ObservableObject`/`RelayCommand`). The three MM1-family trainers (`MightAndMagic1Trainer`, `BardsTale1Trainer`, `PoolOfRadianceTrainer`) reference it instead of carrying their own copies; each keeps only its game-specific locators/scanners locally. `DragonWarsTrainer`, `MinesOfTitanTrainer`, `WarOfTheLanceTrainer`, `WastelandTrainer`, `AmberstarTrainer`, `EyeOfTheBeholder1Trainer`, `JumpmanLivesTrainer`, and `Wizardry1Trainer` also reference it, pulling both `GameTrainers.Common.Memory` and `GameTrainers.Common.Mvvm` (via csproj `<Using>` items — note their `ObservableObject` uses `SetField`) and keeping only their own game-specific locators local (DragonWars its anchor-based `RosterLocator`, Mines of Titan its `IJKM`-anchored `PartyLocator`, War of the Lance its NAT.DAT + strength-block-signature `GameLocator`, Wasteland its structural seven-record `PartyLocator` plus a party-state-header teleport that has no separate locator — the header sits at a fixed offset before the located roster, Eye of the Beholder I its structural six-record `PartyLocator` with no static anchor, Wizardry I its structural six-record `RosterLocator` with no static anchor — the UCSD p-system heap is dynamically allocated so there is no string or byte pattern to anchor to). `DarkDesigns1Trainer` (Dark Designs I: Grelminar's Staff — Softdisk / Big Blue Disk, 1990, by John Carmack) also references it, pulling both `Memory` and `Mvvm`; its `DARKDES.EXE` is **LZEXE 0.91**-compressed (unpacking to 137,616 bytes / 855 relocations), a multi-code-segment (medium/large model) Borland C build with a single DGROUP, whose character buffer lives in BSS. `RosterLocator` uses a **string-anchored primary** — the 34-byte title string `"Dark Designs I : Grelminar's Staff"` — searching a 256 KB window forward for the 15-record character pattern, with a **structural fallback** scanning all readable memory for contiguous 72-byte records, then a content-matched sweep for the game's party working copies so live edits survive its own save. The **72-byte** record (name, status, class, five uint16 LE attributes, level, uint32 experience and next-level threshold, magic current/max, body current/max, gold, four readied-equipment bytes and a ten-byte carried pack) was recovered by **disassembling** the unpacked EXE — the game multiplies a character index by `0x48` at ~300 sites and by 54 at none — and cross-checked against a player-created `DDCHARS.DAT` (one character, "CHRISTOPHER", Fighter L1). Item bytes are ids 0–63 into the EXE's item table, and `ItemBook.All` is indexed by that id, so its order is load-bearing. A second locator, `CreationScanner`, finds the (C)reate screen's **rolled stat pool** (five contiguous uint16 LE values — not a roster record, so `RosterLocator` is blind to it) by signature-scanning the player's five typed numbers as a *multiset*, which makes the lock order-insensitive; its `CharacterRollerViewModel` then taps `R` until the set can be arranged onto the per-attribute minimums, and can also write the pool outright (confirmed live: a written 18 reached the created character, but the already-painted row of numbers is not repainted — say so rather than implying the screen is in sync). The dice were **measured off the running game**, not guessed: 400 automated re-rolls gave `10 + random(5) + random(5)` per value (10–18, mean 14, chi-square *p* ≈ 0.66), so `RollOdds` prices any target exactly, and `FormatCheck` cross-checks it against brute force over all 59,049 outcomes. It additionally ships an **offline `DDCHARS.DAT` editor** (1,224 bytes = 144-byte header + 15 × 72-byte records, no checksum, one-shot `.bak`) that edits inventory, readied equipment and the saved party position, and a References tab with all 16 spells, the 41 obtainable items, and 43 monsters. A **Maps tab** draws the castle's five levels, tracks the party live and teleports it. Each level is a 12,648-byte `DDMAP<n>.DAT` the game reads **verbatim** into one buffer at `DGROUP:0x50F4`, so file and live layout are the same thing: a 32×32×4 wall grid at `0x0000` indexed `x*128 + y*4 + facing`, a 32×32 contents array at `0x1000` indexed `x*32 + y` (bit 7 = mapped, the remaining **seven** bits an event code — 0x35/0x36 stairs, 0x37 chest, 0x38 item, 0x39 ledge — of which anything above 0x3F means "used up", which is how the game retires a looted chest as the byte `0xF7` and a taken item as `0xF8`), two 64-entry text-index tables, 2,320 undecoded bytes, and 127 forty-byte description lines — which is where the room names come from, read out of the map rather than curated. **X grows east, Y grows south**, facing is 0 N / 1 E / 2 S / 3 W and indexes the wall byte directly; that reading is forced by the game's own step tables, by the two item squares it hard-codes by coordinate (`THE  S T A F F` at level 1 (20, 22)) landing on squares the files mark as items, and by the stairways lining up square-for-square across all five levels. `MapLocator` derives the party position (four `uint16` at `DGROUP:0x1320` — the same words the save header carries at `0x08`, which is how that header was finally decoded) from the roster `RosterLocator` already found, at `0xEFC` from the array base or `0xEB4` from the file's first record since the scan can anchor on either, and accepts a candidate only if the map behind it passes **wall reciprocity** (a square's east wall byte equals its eastern neighbour's west wall byte, 3,968 of 3,968 interior pairs on every shipped level) **and text-table consistency** (every description run lands inside the 127 text lines, every line's length prefix fits its 40-byte slot). Both layers are load-bearing and each catches what the other cannot: range checks alone accept an address one 72-byte record off, because a zeroed position block reads as a plausible "in town" position and a shifted window of a real map is still all in-range bytes; and reciprocity alone accepts **113 different offsets** (measured live), because it relates squares a *fixed distance apart* and so survives sliding the whole grid by whole squares, which the few hundred zero bytes in front of the buffer let it do. Only the text tables pin the absolute byte alignment. The cost is that the party must be inside the castle to locate at all. A structural sweep for the same signature is the fallback, and `IMemorySource` exists so `FormatCheck` can drive both over a synthetic address space. Live: located in **1 ms** at the predicted `0xEB4` delta, decoded Ground Level X 16 / Y 31 facing North (matching the save header field-for-field), and read a buffer differing from `DDMAP3.DAT` on disk by 2 content bytes and **0** of 4,096 wall bytes; a teleport was written, read back and reverted. The live teleport writes **X, Y and facing only, never the level** — the game loads a level's map when it processes a stairway, so moving the level word alone strands the party on the wrong map; level changes belong to the game (teleport onto a stairway, take a step) or to the save editor, where the game reloads the matching map itself. "Reveal whole level" sets bit 7 across the contents section, which the game keeps and writes into that level's `DDMAP` file on its next save — the one trainer action that reaches the player's data files. Its RE notes and a strategy guide with full ASCII maps of all five levels live in its committed `docs/`. `ThePerfectGeneral2Trainer` also references it, but is the odd one out: its target is a 16-bit DOS **protected-mode (DPMI)** program whose run-time heap has no stable static signature to anchor a locator to, so it has **no `GameLocator`** — instead it drives Common's `MemorySearcher` as a Cheat-Engine-style value scanner (attach → scan → narrow → pin/freeze) and keeps only its two Confirmed data structures (`PurchaseFormat`, `UnitReference`) local. `BattleTech1Trainer` follows the same value-scanner model for the same reason (its real-mode DOS target's mutable C-Bills/health/skill state has no adjacent constant byte-run to anchor a locator to, so it too has **no `GameLocator`**), but additionally uses Common's `BytePatternScanner` in a `GameDetector` **presence check** that signature-scans for the read-only ASCII tables `BTECH.EXE` maps into guest RAM verbatim; it keeps its Confirmed game-knowledge (`WeaponTable`, `WeaponReference`, `MechReference`, `SkillSheet`, `GameSignatures`) local. `PoolOfRadianceTrainer` intentionally kept its own divergent MVVM, `NativeMethods` and value-scanner and pulls only `ProcessMemory`/`MemoryRegion` from Common (via csproj using-aliases). `QuestForGlory1Trainer` also follows the value-scanner model: Quest for Glory I runs on Sierra's SCI0 interpreter whose heap is dynamically allocated in DOSBox guest RAM each session (no stable static signature), so it uses `MemorySearcher` for scanning; it additionally exposes a **Day/Time editor** (writes the game-clock tick counter and day global directly) and a **Teleport editor** (writes the current room-number global); it keeps only its game-knowledge layer (`GameOffsets`, `RoomBook`, `SkillBook`) local. `DarklandsTrainer` (Darklands — MicroProse, 1992) follows the same value-scanner model but is the most locked-down target: `DARKLAND.EXE` is a **PKLITE-compressed** MS-C binary that a DOS extender relocates into extended memory, so not only is the mutable state (attributes, skills, party Fame, the coin purse) dynamically allocated with no adjacent constant byte-run, but even the static tables are not at a fixed image offset and there is no reliable EXE-string detection signature — so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with five guided scans (Endurance/Strength/Skill/Fame/Florins). It keeps its Confirmed game-knowledge local (`AttributeBook` = six primaries + Divine Favor, `SkillBook` = nineteen skills, `GameFacts` = currency ratios + Fame ladder) plus a **read-only** `SaveFile` reader for the shipped `SAVES\DEFAULT` template (offsets derived from a single sample, so it never writes saves — `test/FormatCheck` validates it against a synthetic fixture). `MoriaTrainer` (The Dungeons of Moria / UMoria 5.5.2 — Koeneke/Wilson, 1988) follows the same value-scanner model: UMoria is a DJGPP v2.01-compiled 32-bit **DPMI** roguelike whose flat data segment is allocated at a session-specific linear address by CWSDPMI, so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with 14 guided scans (chp/maxhp/cmana/mhp/au/exp/lev/str/int/wis/dex/con/chr/food). It additionally exposes a **relative-scan teleport** that locates `char_row`/`char_col` (two `int16` globals that track cardinal moves) by snapshotting an unknown-value Int16 baseline, walking one square in-game, and narrowing by Increased/Decreased until two candidates remain — a workflow unique among the value-scanner trainers because UMoria is the only one with a single character that steps cardinal directions. It keeps its Confirmed game-knowledge local (`PlayerFormat` = the `player_type` struct offsets + the 3..18/100 stat encoding + the cave cell constants, `RaceBook`/`ClassBook`/`SpellBook`/`ItemBook`/`LevelBook`/`MonsterBook`/`ParagraphBook` = the eight races, six classes, 31+31 spells, 27 item categories, 51-level descent reference, a curated 29-creature roster including the Balrog, and the recall-paragraph renderer) — `test/FormatCheck` validates the stat encoding round-trips, the counts, and the scan helpers. `ColonizationTrainer` (Sid Meier's Colonization — MicroProse, 1994) also references Common but is architecturally distinct: its **primary** feature is an **offline save-game editor**, not a live trainer. The `COLONYxx.SAV` format is a flat little-endian serialization (signature `"COLONIZE"`, no checksum), so it edits fields in place through typed record views — the human player's **gold** is a 4-byte value at nation-record offset `0x2A`, whose absolute position is computed from the header's `colony_count`/`unit_count` (sections after the 390-byte header are count-addressed, never fixed), verified byte-for-byte against the shipped saves and three community sources that decoded `VICEROY.EXE`. It keeps its own game layer local (`SaveFormat` offset table, `Bytes` LE accessor, `SaveGame`/`NationRecord`/`ColonyRecord` views, and the goods/unit/terrain/profession/building/founding-father/nation reference books) and additionally exposes Common's `MemorySearcher` as a live value scanner for gold/tax/bells (the real-mode overlaid `VICEROY.EXE` has no session-stable signature to anchor a locator to, so there is **no `GameLocator`**); `test/FormatCheck` round-trips a synthetic save byte-for-byte and, when the copyrighted `.games\COLONY00.SAV` is present, asserts the empirically-confirmed values (map 58×72, year 1492, England, 0 gold/0% tax). `ImperialismIITrainer` (Imperialism II — Frog City / SSI, 1999) also references Common but is the repo's **only native 32-bit Windows target**: it attaches straight to `Imperialism II.exe` (the same `ProcessMemory`/`MemorySearcher`, confirmed to have no DOSBox assumptions — validated live against the running game at 717 regions / ~171 MiB) and drives `MemorySearcher` as a value scanner with guided Treasury (Int32) / Resource (Int16) / Labour (Int16) presets. Unusually for a value-scanner-style trainer it also **has a `GameLocator`** (one-click auto-locate, no scan): the shipped linker map (`Imperialism II.map`) names the whole data model — playable powers are `TGreatPower : TCountry`, treasury a signed 32-bit `long`, warehouse stockpiles signed 16-bit `short` per commodity — but the **shipped exe is a later build than the map** (June vs January 1999), so the map's *addresses* are stale. Because the exe is a native, no-ASLR image, a live pointer scan recovered a stable June-build anchor (static global `0x760650` → nation object; treasury at `+0x130`, warehouse at `+0xDD4`), which `GameLocator`/`NationLayout` follow and validate (vtable + plausible treasury + sane warehouse), falling back to `MemorySearcher` if a build differs. There is **no save editor** (the `.imp` save has no matching map to parse). It keeps its `GameLocator`/`NationLayout` and `CommodityBook` (the 28 Age-of-Exploration goods from the game manual — the exe's internal name table is the *industrial* set and is wrong for AoE; ten goods were confirmed against the live warehouse) local, and `FormatCheck` asserts the commodity table, the layout/validation logic, and the pure scanner helpers. `RailroadTycoonTrainer` (Sid Meier's Railroad Tycoon — MicroProse, 1990) also references Common and is a **DOS-under-DOSBox** target (attaches to the emulator, not a native game), but unlike the repo's other DOSBox value-scanner trainers it **has a string-anchored `GameLocator`** in the spirit of the MM1 family: `GAME.EXE` v455.00 is an EXEPACK-packed, overlay-linked Microsoft-C build whose data is almost entirely static, so the player's **cash is a signed 16-bit word in units of $1,000 at `DGROUP:0x957A`** (live write-test confirmed — writing a sentinel there drove the on-screen cash panel) and the **year is a `uint16` at `DGROUP:0x96C0`** (confirmed live and by the static era-gate comparisons). The locator scans the DOSBox host for the report-label string `"Outstanding Loans: "` (DGROUP `0x24A8`), validates with `"Stockholders Equity: "` (`0x24BC`) plus a plausible year, and reads cash/year at their fixed offsets — a one-click auto-locate that pins Cash + Year with **no scan** (verified live: located in ~0.2 s, correct values, round-trip write OK), with `MemorySearcher` as the build-independent fallback (a different-build disasm reported cash at `0x95AA`; ours is `0x957A`). There is **no `GameLocator`-less** value-only design here and **no save editor**: the `.SVE` is a variable-length, count-keyed multi-region serialization (overlay #39) in which cash is not a discrete field, so live memory is the only verifiable path. It keeps its `RtLayout`/`GameLocator` and its `LocomotiveBook`/`GameFacts` reference tables local (the three engine rosters double as the startup copy-protection quiz answer key — the buy-list keeps `2-6-6-2 Mallet`/`'F' Series Diesel` while the quiz shows the aliases `Challenger`/`F3A-Series`), and `FormatCheck` asserts the reference tables, the `RtLayout` offsets/segment-validation/conversions, and the pure scanner helpers. Its RE (EXEPACK unpack, the `DS = 0x164B` DGROUP proof, the live cash write-test, the save-format teardown) and a play/strategy guide live in its committed `docs/`. `AmberstarTrainer` (Amberstar — Thalion Software, 1992) also references Common and follows the structural-scan model: Amberstar was originally developed for the Atari ST (Motorola 68000, **big-endian**) and ported to PC as the IBM AT V1.34 build, so all multi-byte values in its character records are big-endian (the high byte comes first — the single most important detail for correct parsing on PC). The party is an array of up to six contiguous 1146-byte records; each starts with a `00 FF` magic header and is validated by type = Person, plausible gender/race/class, skill bytes in 0..99, big-endian attributes in 1..999, HP max > 0, and an ASCII name starting with a letter. The roster address changes every DOSBox session (no static anchor), so `PartyLocator` walks every readable region looking for a window of six records matching that shape exactly — occupied slots pack from slot 0, followed by empty slots. It keeps its game-knowledge layer local (`CharacterFormat` = the 1146-byte offset table with big-endian constants and ailment flags, `CharacterRecord` = typed mutable view with BE Word/Long accessors, `SpellBook`/`RaceBook`/`ClassBook` = the 96 spells across four schools, 7 races, 8 classes) — `FormatCheck` asserts the decoded fields, name round-trip, IsOccupied check, reference tables, and set operations. Its RE notes and strategy guide live in its committed `docs/`. The `PARTYDAT.SAV` save file uses an unknown compression method and is not directly editable; this trainer edits live memory only. `BeachHead2000Trainer` (BeachHead 2000 — Digital Fusion / WizardWorks, 2000) also references Common and is the repo's **second native 32-bit Windows target** (after `ImperialismIITrainer`): it attaches straight to `Bh.exe` (shipped in the Steam "BeachHead Gold Edition" package's `509610` folder) — no emulator. The game is a no-ASLR 32-bit x86 build (image base `0x00400000`), but its mutable state (health, ammo, score, current level) is heap-allocated with no adjacent constant byte-run to anchor a locator to (confirmed by dumping the `.data` section and scanning the full process memory), so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with six guided scans (Health/Bullets/Projectiles/Missiles/Score/Level — all Int32). It additionally exposes a **level-file editor** (like `ColonizationTrainer`'s save editor): the shipped `Level_00`…`Level_60` files in the `beachhead\` subdirectory are plain-text scripts defining starting `Ammo <bullets> <projectiles> <missiles>`, `Time <seconds>`, `Aggression <tank> <jet> <heliGun> <heliRocket>` (1–9), `Artillery <0|1>`, and `Object`/`ObjectInc` blocks for enemy waves (Barge/Tank/APC/Bomber/Jet/Helicopter1/Helicopter2/C130) terminated by `End`; `LevelFile` parses, edits, and round-trips them without losing comments, blank lines, or unknown properties. It keeps its Confirmed game-knowledge local (`GameFacts` = process name, image base, 61 levels, aggression range, max ammo; `WeaponInfo` = 3 weapons; `EnemyInfo` = 9 enemies; `ControlInfo` = 10 controls) — `test/FormatCheck` validates the constants, the level-file parse/round-trip/edge cases, the scan-value helpers, and the frozen-value view-model logic. `SwordOfAragonTrainer` (Sword of Aragon — SSI, 1989) also references Common and is, like `ColonizationTrainer`, primarily an **offline save editor** with a live tab second. The defining fact about the target: it is a compiled **QuickBASIC 3.0** DOS program linked against the **BRUN30** run-time module, which is *not* in the executable image, so the code stream is a series of far calls into an absent module with inline argument blocks and **does not disassemble** — a full Ghidra auto-analysis of `SWORD.EXE` recovered ~350 instructions from a 40 KB image and no cross-references to any interesting string. Hence **no variable address is statically recoverable and none is hard-coded**, and all the reverse engineering went through the *data*, which turned out to hold the whole game database. `ARAGON.HS<letter>` is plain CRLF/comma ASCII (286 lines: date+cursor, an unproven line, then `wealth,score,income,maintenance`, then 20 city blocks of 14 lines carrying population/morale/loyalty/health/tax/city-gold/recruits/position, a per-month delta row, and seven `devel,cost,resrc,prod,…` economy lines) and `ARAGON.HR<letter>` is exactly 80 fixed 100-byte roster records split **20 character slots + 60 unit slots** (the limits the game itself enforces), so both are edited one field/offset at a time with everything untouched round-tripped verbatim and a one-shot `.bak` taken before the first write. The roster layout is proved, not guessed: summing the unit and equipment price tables that `SWORD.EXE` carries as QuickBASIC `DATA` text reproduces each record's stored make/train/upkeep and stacking size for **623 of 623** occupied records across the 15 shipped saves and 16 distinct (player class, unit type) pairs — which also established the class purchase discounts (Warrior ×0.5 on Infantry only; Knight ×0.75 on Cavalry *and* Mounted Infantry, which the rule book omits; Ranger ×0.75 on Bowmen and Horse Bowmen; characters never discounted) and that fractional totals round half away from zero. It has **no `GameLocator`** of the RailroadTycoon kind but is not a blind value scanner either: QuickBASIC precedes every string literal with a 4-byte `(length, DS-offset)` descriptor and the whole literal pool sits at one constant file→`DS` delta per executable (`SWORD` +0x2F20, `ARAGON` −0x3FE0, `HEXWAR` −0x3AA0), so `Memory/DgroupLocator` signature-scans DOSBox for the 38-byte City Status banner whose `DS:` offset is known, accepts a hit only when at least two of the three other literals also line up at their expected relative offsets (`MinValidators` = 2, i.e. a three-of-four match at minimum, with the count reported to the user), derives `DS:0000`, and then searches only that 64 KiB segment — with Common's `MemorySearcher` as the build-independent fallback. Because QuickBASIC 3.0 predates Microsoft's move to IEEE, gold/income/upkeep/experience are **Microsoft Binary Format** singles, handled by a local `Game/Mbf`; positive MBF singles happen to stay monotonic when read as unsigned Int32, which is what makes Increased/Decreased narrowing work on gold. The startup copy protection is **answered, not patched**: the complete 13-city × 4-field answer key sits as plain literals in `SWORD.EXE` at 0x7250–0x7444 and ships in `ProtectionBook` (a code patch is not derivable anyway, per the disassembly problem above), so no game executable is ever modified. Game-knowledge stays local (`GameFacts`, `Mbf`, `UnitBook`, `RosterFormat`/`RosterRecord`/`RosterFile`, `CsvRow`/`CityRecord`/`KingdomFile`, `SaveSet`/`SaveBackup`, `CityBook`/`SpellBook`/`ProtectionBook`/`TerrainBook`); `test/FormatCheck` runs 457 checks with the corpus present and 272 without — MBF round-trips and monotonicity, the cost model against twelve worked examples plus the whole 623-record corpus and its 16 class/type pairs (both figures asserted, not merely printed), the documented hard limits pinned to literals rather than to the constants the clamps themselves use, table invariants, synthetic roster/kingdom fixtures that assert clamping, rejection of malformed files and byte-identical unedited records, and every shipped save parsed and round-tripped byte-for-byte (the real-save group is skipped with a note, not failed, when the copyrighted files are absent). `ARAGON.HT<letter>` (the 24×24 world grid, four `int16` per hex) is deliberately neither read nor written because its per-hex layout is only partially decoded. Its RE notes and a play/strategy guide with maps live in its committed `docs/`. `PiratesTrainer` (Sid Meier's Pirates! — MicroProse, 1987, IBM version 432.02) also references Common and, like `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`** rather than being a blind value scanner. Its target needs explaining before anything else: the shipped distribution is a DOS conversion of the original *self-booting* release. `PIR.EXE` (1,983 bytes) is not the game — it is a shim that opens the raw floppy images `DISK1`/`DISK2`/`DISKS` as ordinary files, hooks **INT 80h** (an `INT 13h`-style sector read/write whose seek is `((track*2+head)*spt + sector-1)*512`, with `spt` 9 for the game disks and 4 for the save disk), **INT 81h** (select disk, `AL` 1/2/else) and **INT 82h** (a keyboard poll where scancode `0x44` = **F10** restores the saved interrupt table and exits to DOS), then EXECs `DISKP`. `DISKP` is the game: a 163,952-byte MZ image whose first 32 bytes are a relocated segment table putting `DGROUP` at image paragraph `0x1124`, so `dgroupOffset = fileOffset − 0x112B0` and **every global has a constant DGROUP offset**. `GameLocator` sweeps DOSBox for `"COPYRIGHT (C)  1987  MICROPROSE INC."` (DGROUP `0x0183`), derives `DGROUP:0000 = hit − 0x0183`, and accepts the candidate only if the eight-byte `"PIRATES!"` save magic (`0x4128` — only the *first* eight bytes are constant; the second copy at `0x4130` is the save block itself) and the `JAN…DEC` month table (`0x31C9`) also match, the era code and date decode sanely, **and** the settlement table at `0x4240` parses as 24-byte records — the last check being the important one, because that table is loaded from disk at run time and so cannot be faked by a buffered copy of the program image. Its RE notes and a strategy guide with ASCII maps of all 10 dungeon levels live in its committed `docs/`. `Civilization3ConquestsTrainer` (Sid Meier's Civilization III: Conquests — Firaxis Games / Atari, 2003; this build is the Steam *Civilization III Complete* package, ruleset **v1.22**, PE-timestamped 2015-03-19) also references Common and is the repo's **third native 32-bit Windows** target after `ImperialismIITrainer` and `BeachHead2000Trainer`: it attaches straight to `Civ3Conquests.exe` — no emulator, no guest-address translation. So the work here was transcription plus independent proof rather than teardown, and nothing was taken on trust: five unrelated values were cross-checked against `conquests.ini`, a file the game writes and which therefore cannot be circular with a memory read — `p_preferences` read `0x1E3E300D` against ini `Preferences=00011110001111100011000000001101`, `p_toggleable_rules` `0x6009` against `Rules=…0110000000001001`, `p_game_difficulty` `7` against `Difficulty=7`, `Map.Seed` `283554621` against `WorldSeed=283554621`, and `leaders[1..12].RaceID` `2,8,1,5,4,7,6,3,9,10,11,12` against `ActualCiv0..11` in order. The **defining fact about the target**, and the reason this is a locator trainer rather than a value-scanner one, is that **Civ3 obfuscates the treasury**: a `Leader` carries `Gold_Decrement` at `+0x44` and `Gold_Encoded` at `+0x48` whose *sum* is your gold, seeded differently for every civ in every game (three civs read `-12345/12355`, `-12342/12352`, `-12337/12347`, all summing to 10), so the number on the top bar is **never in memory** and a Cheat-Engine exact-value scan for it cannot work at all — which is why `LiveScannerViewModel`'s treasury guide tells the user to run an *unknown-value* scan narrowed by Changed instead, why writes go to the **encoded half only** (the decrement is the game's key), and why a freeze **re-encodes against a fresh read of the key every tick** rather than replaying captured bytes. Confirmed live end to end: `10 → 12345 → 10` with the key untouched, plus a scratch write to `Golden_Age_End` (`-1 → 24301 → -1`) proving `WriteProcessMemory` reaches the game at all. `GameLocator` has **two chains and no hard-coded VA**: chain A adds the recovered RVAs to the module base the OS reports and accepts nothing until **all 32 leader slots** simultaneously carry the `'LEAD'` tag, an `ID` equal to their own index, a shared vtable inside a `.rdata` range **parsed out of the mapped PE header** (`PeImage`, which also supplies the `TimeDateStamp` build fingerprint) rather than a baked constant, `RaceID` in `[-1,32)`, rate sliders totalling exactly 10, plausible era/city/unit counts, an embedded `'CULT'` object whose `CivID` agrees, and a decodable treasury — `ID == index` being the load-bearing one, because only the true base *and* the true stride `0x20E4` satisfy it 32 times running; chain B re-derives the array from the game's **own code** by sweeping `.text` for the inlined array walk (`add r32, sizeof(Leader)` within 16 bytes of `cmp r32, one-past-end`), keeping pairs whose implied base lands in `.data`, taking the modal stride and the lowest base in that cluster, then running the same validation. The stride is triple-confirmed: struct arithmetic, a brute force over `[0x1000,0x9000]` leaving exactly one survivor, and the game's own loop at `0x50C1BD` (`add ebp,0x20E4` / `cmp ebp,0xAB7318`, and `0xA75698 + 32 × 0x20E4 = 0xAB7318` exactly). Measured live at **~3 ms, 32/32 slots**, correct civ (`Egypt — Cleopatra`), map 130×130 with `TileCount == W × H ÷ 2` (Civ3's staggered grid, which is itself used as a validator). Two `Unit_Body` fields **read backwards** and both the grid and the docs say so: `Damage` at `+0x30` is hit points *lost* and `Moves` at `+0x34` is movement *spent*, so "full heal" and "refresh moves" write **zero**; max hit points are not stored at all (derived from unit type plus veteran level by `Unit_get_max_hp` at `0x5CD180`). Civilizations and unit types are **read out of the loaded `BIC`** (`Races` at `+0x3CC8`, `UnitTypes` at `+0x3CD8`, counts at `+0x8AC`/`+0x8A8`, strides `0x974`/`0x138` recovered by brute force under `Table[i].ID == i` and re-verified at run time) rather than curated, because Conquests ships nine scenarios and the community ships thousands of mods that each substitute their own roster — a baked table would be right only for the unmodified epic game; live this yields all 32 civs and 141 unit types with correct attack/defence/movement/cost. The **one real gap is deliberate and marked**: the C3X header's own `field_XX` anchors agree with arithmetic through `City_Body + 0x54` and then **drift by `0x18`**, so population, corruption, per-turn incomes, the build queue and the city name sit at offsets nobody has pinned — `Civ3Layout.CityTrustedPrefixEnd` marks the boundary, only the anchored prefix (position, stored food, stored shields, cultural level) is surfaced, and the fix is a session that actually has cities (the probed game was at turn 0 with `p_cities->LastIndex == -1`) or a decompile of `City_recompute_happiness` (`0x4C4660`) / `City_recompute_commerce` (`0x4B7770`), **not** a guess. Likewise the four tile visibility masks are `[Inferred]`, so "Reveal map" is gated behind an explicit acknowledgement rather than offered as a one-click button and every tile is checked for its own `'TILE'` tag at `+0x44` before it is written to. There is **no tech granting** (C3X names only the function `Leader_has_tech` at `0x56D5A0`; no tech bit-array field exists in the header), **no gold-per-turn editing** (not stored — `Leader_recompute_economy` at `0x56D420` recomputes it from the cities each turn), no "always your turn" flag, and writes are suppressed outright when `p_is_pbem_game`/`p_is_offline_mp_game` are set. ## Build, Test, and Development Commands

- Root launcher: from the repo root run `.\Run.ps1` for an interactive menu of every trainer, or `.\Run.ps1 -Trainer <name|number>` to pick one directly (`-List` prints the menu and exits). It discovers any top-level folder that contains its own `Run.ps1` and forwards the shared options below to it.
- Per-trainer: `.\Run.ps1` inside each trainer folder (including `KeefTrainer`, which now has one). Restores, builds Release, and launches; a UAC prompt appears because the app manifests request admin for `Read/WriteProcessMemory`.
- Every `Run.ps1` (root and per-trainer) exposes the **same** options: `-Configuration Debug|Release` (default Release), `-Clean` (remove bin/obj first), `-NoBuild` (skip build, launch the existing exe), `-NoRun` (build only), `-Test` (run the verification harness; warns if the trainer has none), and `-Publish` (single self-contained win-x64 exe, skips launch).
- Direct: `dotnet build <project>.csproj -c Release` / `dotnet run --project <test-project>`.

## Coding Style & Naming Conventions

C# targeting `net8.0-windows` or `net9.0-windows`, **x64**, with `Nullable` and `ImplicitUsings` enabled. No `.editorconfig`, linter, or formatter is committed — match the surrounding file: 4-space indent, file-scoped namespaces, `sealed` classes, PascalCase members, `_camelCase` fields, `const` hex for offsets, and XML `///` docs on public members. Keep reverse-engineered constants in the game layer; follow the read-validate-write pattern so a shifted layout is never corrupted.

## Testing Guidelines

There is no xUnit/NUnit suite. Trainers that have one use a headless console harness — usually `FormatCheck` (`net8.0` or `net8.0-windows`), or `Verify` in `SwordOfTheSamuraiTrainer` — that asserts parsers against captured dumps/save files and exits 0 (pass) or 1 (fail). The GUI cannot be smoke-tested headlessly — it needs an interactive desktop and a running game. Keep the harness green.

## Commit & Pull Request Guidelines

The root repository has no commit history yet. Per the sibling projects, write imperative, sentence-case subjects (join related changes with a semicolon); describe which game state a change reads/writes and how it was confirmed against the live game.
