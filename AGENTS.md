# Repository Guidelines

A collection of independent, Windows-only C#/WPF **live-memory trainers** for classic games — mostly DOS titles running under **DOSBox / DOSBox-X**, plus two native 32-bit Windows titles (`ImperialismIITrainer` and `BeachHead2000Trainer`). Each trainer attaches to the running process (the emulator, or the game itself for the native target), signature-scans or value-scans its RAM to locate game state at runtime (addresses are never hard-coded), and reads/writes it live — with freeze toggles, "max" buttons, and, for some titles, offline save editing. Several also carry a reverse-engineering workspace behind their offsets.

## Project Structure & Module Organization

Nearly every top-level folder is a **self-contained trainer** with its own solution/project, `README.md`, a PowerShell run script (usually `Run.ps1`), and (mostly) its own `AGENTS.md` — read the per-project `AGENTS.md`/`README.md` before working inside one:

- `AirborneRangerTrainer/`, `AlternateRealityTrainer/`, `AmberstarTrainer/`, `AutoduelTrainer/`, `BardsTale1Trainer/`, `BattleTech1Trainer/`, `BeachHead2000Trainer/`, `ColonizationTrainer/`, `DarklandsTrainer/`, `DragonWarsTrainer/`, `ImperialismIITrainer/`, `KeefTrainer/`, `LordsOfTheRealmTrainer/`, `MightAndMagic1Trainer/`, `MinesOfTitanTrainer/`, `MoriaTrainer/`, `PiratesTrainer/`, `PoolOfRadianceTrainer/`, `QuestForGlory1Trainer/`, `RailroadTycoonTrainer/`, `ShogunTrainer/`, `SwordOfAragonTrainer/`, `SwordOfTheSamuraiTrainer/`, `SyndicatePlusTrainer/`, `ThePerfectGeneral2Trainer/`, `WarOfTheLanceTrainer/`, `WastelandTrainer/`.

`WastelandTrainer/` (Wasteland — Interplay/EA, 1988) is a full trainer: `src/WastelandTrainer/` (`net8.0-windows`, references `GameTrainers.Common` for both `Memory` and `Mvvm`), a `test/FormatCheck/` harness, its own `.sln`/`Run.ps1`/`README.md`/`AGENTS.md`, and Party/Inventory/References/Maps tabs. It locates the party by **structure** (an array of seven contiguous 256-byte records that pack from slot 0) rather than by a static anchor, and teleports by writing the party X/Y in the party-state header that precedes the roster. Its captured RAM dumps (`*.bin`, `*.csv`, `memdump.md`) live under `.data/` (git-ignored by `.*/`) — never `git add` the multi-hundred-MB dumps.

Layout varies: some use a single `Trainer/` project (no `.sln`), others `src/<Name>/` with a `.sln` and a `test/FormatCheck/` harness. `MightAndMagic1Trainer` is the architectural template the others were ported from. Common layers: Win32 P/Invoke (`Native*.cs`), process/guest-memory access, a game-knowledge layer holding all reverse-engineered offsets as constants, and hand-rolled MVVM (`ObservableObject`/`RelayCommand`).

`GameTrainers.Common/` is a shared library that extracts the game-agnostic plumbing out of that duplication: `GameTrainers.Common.Memory` (process/guest-memory access — `ProcessMemory`/`MemoryRegion`, `NativeMethods`, `MemorySearcher`, `MemoryDumper`, `DumpComparer`, `BytePatternScanner`, `GlobalHotkeys`, `KeyboardSender`) and `GameTrainers.Common.Mvvm` (`ObservableObject`/`RelayCommand`). The three MM1-family trainers (`MightAndMagic1Trainer`, `BardsTale1Trainer`, `PoolOfRadianceTrainer`) reference it instead of carrying their own copies; each keeps only its game-specific locators/scanners locally. `DragonWarsTrainer`, `MinesOfTitanTrainer`, `WarOfTheLanceTrainer`, `WastelandTrainer`, and `AmberstarTrainer` also reference it, pulling both `GameTrainers.Common.Memory` and `GameTrainers.Common.Mvvm` (via csproj `<Using>` items — note their `ObservableObject` uses `SetField`) and keeping only their own game-specific locators local (DragonWars its anchor-based `RosterLocator`, Mines of Titan its `IJKM`-anchored `PartyLocator`, War of the Lance its NAT.DAT + strength-block-signature `GameLocator`, Wasteland its structural seven-record `PartyLocator` plus a party-state-header teleport that has no separate locator — the header sits at a fixed offset before the located roster). `ThePerfectGeneral2Trainer` also references it, but is the odd one out: its target is a 16-bit DOS **protected-mode (DPMI)** program whose run-time heap has no stable static signature to anchor a locator to, so it has **no `GameLocator`** — instead it drives Common's `MemorySearcher` as a Cheat-Engine-style value scanner (attach → scan → narrow → pin/freeze) and keeps only its two Confirmed data structures (`PurchaseFormat`, `UnitReference`) local. `BattleTech1Trainer` follows the same value-scanner model for the same reason (its real-mode DOS target's mutable C-Bills/health/skill state has no adjacent constant byte-run to anchor a locator to, so it too has **no `GameLocator`**), but additionally uses Common's `BytePatternScanner` in a `GameDetector` **presence check** that signature-scans for the read-only ASCII tables `BTECH.EXE` maps into guest RAM verbatim; it keeps its Confirmed game-knowledge (`WeaponTable`, `WeaponReference`, `MechReference`, `SkillSheet`, `GameSignatures`) local. `PoolOfRadianceTrainer` intentionally kept its own divergent MVVM, `NativeMethods` and value-scanner and pulls only `ProcessMemory`/`MemoryRegion` from Common (via csproj using-aliases). `QuestForGlory1Trainer` also follows the value-scanner model: Quest for Glory I runs on Sierra's SCI0 interpreter whose heap is dynamically allocated in DOSBox guest RAM each session (no stable static signature), so it uses `MemorySearcher` for scanning; it additionally exposes a **Day/Time editor** (writes the game-clock tick counter and day global directly) and a **Teleport editor** (writes the current room-number global); it keeps only its game-knowledge layer (`GameOffsets`, `RoomBook`, `SkillBook`) local. `DarklandsTrainer` (Darklands — MicroProse, 1992) follows the same value-scanner model but is the most locked-down target: `DARKLAND.EXE` is a **PKLITE-compressed** MS-C binary that a DOS extender relocates into extended memory, so not only is the mutable state (attributes, skills, party Fame, the coin purse) dynamically allocated with no adjacent constant byte-run, but even the static tables are not at a fixed image offset and there is no reliable EXE-string detection signature — so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with five guided scans (Endurance/Strength/Skill/Fame/Florins). It keeps its Confirmed game-knowledge local (`AttributeBook` = six primaries + Divine Favor, `SkillBook` = nineteen skills, `GameFacts` = currency ratios + Fame ladder) plus a **read-only** `SaveFile` reader for the shipped `SAVES\DEFAULT` template (offsets derived from a single sample, so it never writes saves — `test/FormatCheck` validates it against a synthetic fixture). `MoriaTrainer` (The Dungeons of Moria / UMoria 5.5.2 — Koeneke/Wilson, 1988) follows the same value-scanner model: UMoria is a DJGPP v2.01-compiled 32-bit **DPMI** roguelike whose flat data segment is allocated at a session-specific linear address by CWSDPMI, so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with 14 guided scans (chp/maxhp/cmana/mhp/au/exp/lev/str/int/wis/dex/con/chr/food). It additionally exposes a **relative-scan teleport** that locates `char_row`/`char_col` (two `int16` globals that track cardinal moves) by snapshotting an unknown-value Int16 baseline, walking one square in-game, and narrowing by Increased/Decreased until two candidates remain — a workflow unique among the value-scanner trainers because UMoria is the only one with a single character that steps cardinal directions. It keeps its Confirmed game-knowledge local (`PlayerFormat` = the `player_type` struct offsets + the 3..18/100 stat encoding + the cave cell constants, `RaceBook`/`ClassBook`/`SpellBook`/`ItemBook`/`LevelBook`/`MonsterBook`/`ParagraphBook` = the eight races, six classes, 31+31 spells, 27 item categories, 51-level descent reference, a curated 29-creature roster including the Balrog, and the recall-paragraph renderer) — `test/FormatCheck` validates the stat encoding round-trips, the counts, and the scan helpers. `ColonizationTrainer` (Sid Meier's Colonization — MicroProse, 1994) also references Common but is architecturally distinct: its **primary** feature is an **offline save-game editor**, not a live trainer. The `COLONYxx.SAV` format is a flat little-endian serialization (signature `"COLONIZE"`, no checksum), so it edits fields in place through typed record views — the human player's **gold** is a 4-byte value at nation-record offset `0x2A`, whose absolute position is computed from the header's `colony_count`/`unit_count` (sections after the 390-byte header are count-addressed, never fixed), verified byte-for-byte against the shipped saves and three community sources that decoded `VICEROY.EXE`. It keeps its own game layer local (`SaveFormat` offset table, `Bytes` LE accessor, `SaveGame`/`NationRecord`/`ColonyRecord` views, and the goods/unit/terrain/profession/building/founding-father/nation reference books) and additionally exposes Common's `MemorySearcher` as a live value scanner for gold/tax/bells (the real-mode overlaid `VICEROY.EXE` has no session-stable signature to anchor a locator to, so there is **no `GameLocator`**); `test/FormatCheck` round-trips a synthetic save byte-for-byte and, when the copyrighted `.games\COLONY00.SAV` is present, asserts the empirically-confirmed values (map 58×72, year 1492, England, 0 gold/0% tax). `ImperialismIITrainer` (Imperialism II — Frog City / SSI, 1999) also references Common but is the repo's **only native 32-bit Windows target**: it attaches straight to `Imperialism II.exe` (the same `ProcessMemory`/`MemorySearcher`, confirmed to have no DOSBox assumptions — validated live against the running game at 717 regions / ~171 MiB) and drives `MemorySearcher` as a value scanner with guided Treasury (Int32) / Resource (Int16) / Labour (Int16) presets. Unusually for a value-scanner-style trainer it also **has a `GameLocator`** (one-click auto-locate, no scan): the shipped linker map (`Imperialism II.map`) names the whole data model — playable powers are `TGreatPower : TCountry`, treasury a signed 32-bit `long`, warehouse stockpiles signed 16-bit `short` per commodity — but the **shipped exe is a later build than the map** (June vs January 1999), so the map's *addresses* are stale. Because the exe is a native, no-ASLR image, a live pointer scan recovered a stable June-build anchor (static global `0x760650` → nation object; treasury at `+0x130`, warehouse at `+0xDD4`), which `GameLocator`/`NationLayout` follow and validate (vtable + plausible treasury + sane warehouse), falling back to `MemorySearcher` if a build differs. There is **no save editor** (the `.imp` save has no matching map to parse). It keeps its `GameLocator`/`NationLayout` and `CommodityBook` (the 28 Age-of-Exploration goods from the game manual — the exe's internal name table is the *industrial* set and is wrong for AoE; ten goods were confirmed against the live warehouse) local, and `FormatCheck` asserts the commodity table, the layout/validation logic, and the pure scanner helpers. `RailroadTycoonTrainer` (Sid Meier's Railroad Tycoon — MicroProse, 1990) also references Common and is a **DOS-under-DOSBox** target (attaches to the emulator, not a native game), but unlike the repo's other DOSBox value-scanner trainers it **has a string-anchored `GameLocator`** in the spirit of the MM1 family: `GAME.EXE` v455.00 is an EXEPACK-packed, overlay-linked Microsoft-C build whose data is almost entirely static, so the player's **cash is a signed 16-bit word in units of $1,000 at `DGROUP:0x957A`** (live write-test confirmed — writing a sentinel there drove the on-screen cash panel) and the **year is a `uint16` at `DGROUP:0x96C0`** (confirmed live and by the static era-gate comparisons). The locator scans the DOSBox host for the report-label string `"Outstanding Loans: "` (DGROUP `0x24A8`), validates with `"Stockholders Equity: "` (`0x24BC`) plus a plausible year, and reads cash/year at their fixed offsets — a one-click auto-locate that pins Cash + Year with **no scan** (verified live: located in ~0.2 s, correct values, round-trip write OK), with `MemorySearcher` as the build-independent fallback (a different-build disasm reported cash at `0x95AA`; ours is `0x957A`). There is **no `GameLocator`-less** value-only design here and **no save editor**: the `.SVE` is a variable-length, count-keyed multi-region serialization (overlay #39) in which cash is not a discrete field, so live memory is the only verifiable path. It keeps its `RtLayout`/`GameLocator` and its `LocomotiveBook`/`GameFacts` reference tables local (the three engine rosters double as the startup copy-protection quiz answer key — the buy-list keeps `2-6-6-2 Mallet`/`'F' Series Diesel` while the quiz shows the aliases `Challenger`/`F3A-Series`), and `FormatCheck` asserts the reference tables, the `RtLayout` offsets/segment-validation/conversions, and the pure scanner helpers. Its RE (EXEPACK unpack, the `DS = 0x164B` DGROUP proof, the live cash write-test, the save-format teardown) and a play/strategy guide live in its committed `docs/`. `AmberstarTrainer` (Amberstar — Thalion Software, 1992) also references Common and follows the structural-scan model: Amberstar was originally developed for the Atari ST (Motorola 68000, **big-endian**) and ported to PC as the IBM AT V1.34 build, so all multi-byte values in its character records are big-endian (the high byte comes first — the single most important detail for correct parsing on PC). The party is an array of up to six contiguous 1146-byte records; each starts with a `00 FF` magic header and is validated by type = Person, plausible gender/race/class, skill bytes in 0..99, big-endian attributes in 1..999, HP max > 0, and an ASCII name starting with a letter. The roster address changes every DOSBox session (no static anchor), so `PartyLocator` walks every readable region looking for a window of six records matching that shape exactly — occupied slots pack from slot 0, followed by empty slots. It keeps its game-knowledge layer local (`CharacterFormat` = the 1146-byte offset table with big-endian constants and ailment flags, `CharacterRecord` = typed mutable view with BE Word/Long accessors, `SpellBook`/`RaceBook`/`ClassBook` = the 96 spells across four schools, 7 races, 8 classes) — `FormatCheck` asserts the decoded fields, name round-trip, IsOccupied check, reference tables, and set operations. Its RE notes and strategy guide live in its committed `docs/`. The `PARTYDAT.SAV` save file uses an unknown compression method and is not directly editable; this trainer edits live memory only. `BeachHead2000Trainer` (BeachHead 2000 — Digital Fusion / WizardWorks, 2000) also references Common and is the repo's **second native 32-bit Windows target** (after `ImperialismIITrainer`): it attaches straight to `Bh.exe` (shipped in the Steam "BeachHead Gold Edition" package's `509610` folder) — no emulator. The game is a no-ASLR 32-bit x86 build (image base `0x00400000`), but its mutable state (health, ammo, score, current level) is heap-allocated with no adjacent constant byte-run to anchor a locator to (confirmed by dumping the `.data` section and scanning the full process memory), so it has **neither a `GameLocator` nor a `GameDetector`**, just `MemorySearcher` with six guided scans (Health/Bullets/Projectiles/Missiles/Score/Level — all Int32). It additionally exposes a **level-file editor** (like `ColonizationTrainer`'s save editor): the shipped `Level_00`…`Level_60` files in the `beachhead\` subdirectory are plain-text scripts defining starting `Ammo <bullets> <projectiles> <missiles>`, `Time <seconds>`, `Aggression <tank> <jet> <heliGun> <heliRocket>` (1–9), `Artillery <0|1>`, and `Object`/`ObjectInc` blocks for enemy waves (Barge/Tank/APC/Bomber/Jet/Helicopter1/Helicopter2/C130) terminated by `End`; `LevelFile` parses, edits, and round-trips them without losing comments, blank lines, or unknown properties. It keeps its Confirmed game-knowledge local (`GameFacts` = process name, image base, 61 levels, aggression range, max ammo; `WeaponInfo` = 3 weapons; `EnemyInfo` = 9 enemies; `ControlInfo` = 10 controls) — `test/FormatCheck` validates the constants, the level-file parse/round-trip/edge cases, the scan-value helpers, and the frozen-value view-model logic. `SwordOfAragonTrainer` (Sword of Aragon — SSI, 1989) also references Common and is, like `ColonizationTrainer`, primarily an **offline save editor** with a live tab second. The defining fact about the target: it is a compiled **QuickBASIC 3.0** DOS program linked against the **BRUN30** run-time module, which is *not* in the executable image, so the code stream is a series of far calls into an absent module with inline argument blocks and **does not disassemble** — a full Ghidra auto-analysis of `SWORD.EXE` recovered ~350 instructions from a 40 KB image and no cross-references to any interesting string. Hence **no variable address is statically recoverable and none is hard-coded**, and all the reverse engineering went through the *data*, which turned out to hold the whole game database. `ARAGON.HS<letter>` is plain CRLF/comma ASCII (286 lines: date+cursor, an unproven line, then `wealth,score,income,maintenance`, then 20 city blocks of 14 lines carrying population/morale/loyalty/health/tax/city-gold/recruits/position, a per-month delta row, and seven `devel,cost,resrc,prod,…` economy lines) and `ARAGON.HR<letter>` is exactly 80 fixed 100-byte roster records split **20 character slots + 60 unit slots** (the limits the game itself enforces), so both are edited one field/offset at a time with everything untouched round-tripped verbatim and a one-shot `.bak` taken before the first write. The roster layout is proved, not guessed: summing the unit and equipment price tables that `SWORD.EXE` carries as QuickBASIC `DATA` text reproduces each record's stored make/train/upkeep and stacking size for **623 of 623** occupied records across the 15 shipped saves and 16 distinct (player class, unit type) pairs — which also established the class purchase discounts (Warrior ×0.5 on Infantry only; Knight ×0.75 on Cavalry *and* Mounted Infantry, which the rule book omits; Ranger ×0.75 on Bowmen and Horse Bowmen; characters never discounted) and that fractional totals round half away from zero. It has **no `GameLocator`** of the RailroadTycoon kind but is not a blind value scanner either: QuickBASIC precedes every string literal with a 4-byte `(length, DS-offset)` descriptor and the whole literal pool sits at one constant file→`DS` delta per executable (`SWORD` +0x2F20, `ARAGON` −0x3FE0, `HEXWAR` −0x3AA0), so `Memory/DgroupLocator` signature-scans DOSBox for the 38-byte City Status banner whose `DS:` offset is known, accepts a hit only when at least two of the three other literals also line up at their expected relative offsets (`MinValidators` = 2, i.e. a three-of-four match at minimum, with the count reported to the user), derives `DS:0000`, and then searches only that 64 KiB segment — with Common's `MemorySearcher` as the build-independent fallback. Because QuickBASIC 3.0 predates Microsoft's move to IEEE, gold/income/upkeep/experience are **Microsoft Binary Format** singles, handled by a local `Game/Mbf`; positive MBF singles happen to stay monotonic when read as unsigned Int32, which is what makes Increased/Decreased narrowing work on gold. The startup copy protection is **answered, not patched**: the complete 13-city × 4-field answer key sits as plain literals in `SWORD.EXE` at 0x7250–0x7444 and ships in `ProtectionBook` (a code patch is not derivable anyway, per the disassembly problem above), so no game executable is ever modified. Game-knowledge stays local (`GameFacts`, `Mbf`, `UnitBook`, `RosterFormat`/`RosterRecord`/`RosterFile`, `CsvRow`/`CityRecord`/`KingdomFile`, `SaveSet`/`SaveBackup`, `CityBook`/`SpellBook`/`ProtectionBook`/`TerrainBook`); `test/FormatCheck` runs 457 checks with the corpus present and 272 without — MBF round-trips and monotonicity, the cost model against twelve worked examples plus the whole 623-record corpus and its 16 class/type pairs (both figures asserted, not merely printed), the documented hard limits pinned to literals rather than to the constants the clamps themselves use, table invariants, synthetic roster/kingdom fixtures that assert clamping, rejection of malformed files and byte-identical unedited records, and every shipped save parsed and round-tripped byte-for-byte (the real-save group is skipped with a note, not failed, when the copyrighted files are absent). `ARAGON.HT<letter>` (the 24×24 world grid, four `int16` per hex) is deliberately neither read nor written because its per-hex layout is only partially decoded. Its RE notes and a play/strategy guide with maps live in its committed `docs/`. `PiratesTrainer` (Sid Meier's Pirates! — MicroProse, 1987, IBM version 432.02) also references Common and, like `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`** rather than being a blind value scanner. Its target needs explaining before anything else: the shipped distribution is a DOS conversion of the original *self-booting* release. `PIR.EXE` (1,983 bytes) is not the game — it is a shim that opens the raw floppy images `DISK1`/`DISK2`/`DISKS` as ordinary files, hooks **INT 80h** (an `INT 13h`-style sector read/write whose seek is `((track*2+head)*spt + sector-1)*512`, with `spt` 9 for the game disks and 4 for the save disk), **INT 81h** (select disk, `AL` 1/2/else) and **INT 82h** (a keyboard poll where scancode `0x44` = **F10** restores the saved interrupt table and exits to DOS), then EXECs `DISKP`. `DISKP` is the game: a 163,952-byte MZ image whose first 32 bytes are a relocated segment table putting `DGROUP` at image paragraph `0x1124`, so `dgroupOffset = fileOffset − 0x112B0` and **every global has a constant DGROUP offset**. `GameLocator` sweeps DOSBox for `"COPYRIGHT (C)  1987  MICROPROSE INC."` (DGROUP `0x0183`), derives `DGROUP:0000 = hit − 0x0183`, and accepts the candidate only if the eight-byte `"PIRATES!"` save magic (`0x4128` — only the *first* eight bytes are constant; the second copy at `0x4130` is the save block itself) and the `JAN…DEC` month table (`0x31C9`) also match, the era code and date decode sanely, **and** the settlement table at `0x4240` parses as 24-byte records — the last check being the important one, because that table is loaded from disk at run time and so cannot be faked by a buffered copy of the program image. The offsets came out of a static teardown driven by the game's own text engine: `DISKP` has no `printf`, but `mov si,<dgroupOffset>` + `call 0x329C`/`0x32AA` copies a named string into a message buffer, which makes every `mov si, imm` in the disassembly resolve to readable text. That is how gold was fixed at `DGROUP:0x4847` as an **unsigned** `int16` (the add routine *saturates* at 0xFFFF; the spend routine prints "Not enough gold."), wealth at `0x4742` in tens of gold and land at `0x4745` in units of 50 acres (both proved by the retirement screen's print sequence, which appends a literal `'0'` and multiplies by 50 respectively), the flat **360-day** calendar at `0x9A9F` (day-of-year) / `0x9A9D` (years) / `0x9A2B` (month = day/30), and the era code at `0x475A` — stored as **0, 2, 3, 4, 5, 6**, not 0–5, which is exactly what makes the date routine's `1560 + 20 × code` produce the six offered start years and is corroborated by the matching disk-descriptor indices. The 1,940-byte saved-game block at `DGROUP:0x4130` is confirmed (one transfer descriptor moves it, and the slot check compares its first eight bytes against the constant `PIRATES!`), but there is **no save editor**: the shipped `DISKS` is an unformatted blank, so the on-disk slot directory could not be validated against a real save. `CityBook`/`FleetSchedule` are **generated** from `DISK1` (six 1,024-byte era blocks at file offset `0x54000 + 0x400 × era`, which is also where transfer descriptor 4 seeks to — an independent check on the seek formula): 32 settlements in 1560 rising to 41 by 1680, each 24 bytes of map X/Y, nation, forts, garrison ÷10, population ÷100 −1, treasury in thousands and a prosperity band, followed by a 12-character name; then two sixteen-byte convoy route rows. Those rows are the Treasure Fleet and Silver Train itineraries — the answer key to the 1987 manual's date-lookup copy protection — and both they *and* their calendar phase come out of the binary (`slot = day/15 − bias + 2 × (era & 1)`, bias 18 for the Fleet and 6 for the Train, which is why the odd-coded eras 1620 and 1660 run a month earlier); reconstructed that way they reproduce the shipped chart entry-for-entry in 11 of 12 itineraries. **Neither copy protection is active in this build**: the disk check cannot fire once every sector comes from a file, and the manual question is absent from the program's complete 589-record display-string table. Everything above was established **statically** — no live run was performed — which is why every constant in `PiratesLayout` carries a `[Confirmed]` or `[Inferred]` marker, `KnownValues` surfaces that distinction in the UI, the auto-locate publishes a captain/date/era/gold summary line for the user to check against the screen, and `MemorySearcher` (guided Gold/Crew/Any-value scans) remains the fallback. `test/FormatCheck` runs 190+ checks with no live game: the generated tables' invariants and spot-checked field values, every convoy stop cross-checked against its own era's settlement table *and* re-derived from the slot arithmetic, three-anchor `ValidateSegment` against a synthetic DGROUP window, `LooksLikeCityRecord` against synthetic records and against every shipped settlement name, the era-code ↔ index mapping, the calendar arithmetic, the reference view-model's era/filter logic, and the scanner helpers through a fake `IScanHost`. `AlternateRealityTrainer` (Alternate Reality: The City — Datasoft / Intellicreations, IBM PC conversion 1987–88) also references Common and, like `PiratesTrainer` and `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`** — reached by a different route, and the route is the point. `AR.EXE` is only a launcher (a Microsoft C 1986 stub that `exec`s `city`/`dungeon`/`arena`/`wilder`/`palace`; run `CITY.EXE 1` for EGA and skip it). `CITY.EXE` is a plain **unpacked** relocatable MZ image — no packer, no extender — but it is a 1987 large-model binary with no symbols whose control flow is almost entirely far calls through relocated pointers, so **Ghidra's auto-analysis recovers only ~138 functions out of 330 KB and the disassembly is a dead end**; do not start there. What worked was the game's **text engine**: every message is a byte-coded template terminated by `0xFF` in which literal text is plain ASCII **with tab (`0x09`) standing in for the space character** (which is why a naive `strings` pass yields `Very⟨tab⟩Thirsty`), and in which `0xB0`/`0xB1`/`0xB2`/`0xB3` mean "print the u32/u16/u8/NUL-terminated string at `DGROUP:⟨operand⟩⟩`". Because those operands are literal data-segment addresses, **the program carries a symbol table for its own display variables**: sweeping `CITY.EXE` for the opcodes and keeping the hits whose operand lands inside the character buffer yields the field map mechanically, and every field was then confirmed against the running game (write STR/INT → the status bar redraws with them; write experience 200,000 → the game levels the character, adds +1 to every attribute, bumps max hit points and recomputes the next-level threshold to 400,000). Ghidra's segment `3d1a` is `DGROUP` and `DGROUP` byte *n* is file offset `0x2DBA0 + n`, agreed by two independent live anchors. The character is one 12,288-byte block at **`DGROUP:0x4EB1`**, written to disk verbatim as `ARCCD`*nn*, and it is the **working copy** rather than a save snapshot — a live scan finds exactly one occurrence of the attribute cells in the whole 222 MiB DOSBox process. `GameLocator` sweeps for the status-bar header literal `Stats STA   CHR   STR   INT   WIS   SKL` (`DGROUP:0x012A`), derives `DGROUP:0000`, and accepts a candidate only when at least two of three further literals (`Experience`, `Hit Points :`, `Magical Flamesword`) also sit at their own offsets **and** the record behind them passes `CharacterFormat.LooksLikeRecord` (printable name; seven attribute records at stride 10 whose current and maximum bytes sit at or below the natural maximum — they read equal in every shipped save, but a Wraith drain was seen live leaving `0, 0, 9`, and an earlier predicate demanding all three agree could not find a drained character at all; plausible level; hit points within their maximum; a next-level threshold at or above the current experience), with a pure structural scan for that same shape available as an **opt-in** fallback (a separate "Scan anyway" button — run automatically against a process that is not the game it will eventually match some unrelated byte run, observed offering a character called `wwwwwwwwww`, and silently attaching to that would let one "Max Everything" click scribble into another program) — measured live at **~40 ms, 3/3 validators**, every decoded field matching the screen. Two details bite anyone editing this trainer: the record stores attributes as `STR INT WIS SKL STA CHR SPD` while the status bar prints `STA CHR STR INT WIS SKL` and has no column for the seventh (Physical Speed, hidden), so `AttributeBook.DisplayOrder` holds the mapping and `FormatCheck` asserts it reproduces the screen; and the two parallel five-word blocks at `0x30`–`0x45` are the hunger/thirst/weariness meters, which the game rewrites every tick and which revert any edit within seconds — **never write there**. There is **no save editor**: the game owns `ARCCD`*nn* and the trainer edits live memory only, so edits reach disk when the player presses **S**. The trainer also recovers **the city's own street map** — every 4,096-byte window in `CITY.EXE` was scored against the 60 building squares the shipped hint file names, and the right one (file offset `0x279F0`, loaded verbatim to `DGROUP − 0x61B0`, `CharacterFormat.DgroupTerrainOffset`) scored **92 of a possible 95** against a runner-up of 59 (that search score also rewarded each building type getting a distinct code; the run-time check is the simpler 60-square count, which the real map passes at 57). One byte per square, `index = (64 − north) × 64 + (east − 1)`: the low nibble is the location type (1 Inn, 2 Tavern, 3 Bank, 4 Shop, 5 Smithy, 6 scenery, 7 Healer, 8 Guild — matching every known coordinate, and there are exactly three code-3 cells in the whole city for the three banks) and `0x40`/`0x20` mark a building block / a wall, which is what lets the map tab draw real streets and a real city wall. `CityTerrain` reads it from the attached process or from the player's own `CITY.EXE` and **never commits it** — it is the game's data — and refuses any candidate block that does not explain at least 80 % of the known building squares, so a bad read cannot be drawn as if it were the city. **Map position is unfound, and the search is unfinished — read `docs/ReverseEngineering.md` §4.5 before re-guessing it.** What was ruled out: five one-step snapshots differenced across a 384 KB window around `DGROUP` (the emulated RAM is one **16 MB** region, so that window was the search, not the space), the same for a twenty-square walk, both a coordinate-pair and a map-pointer hypothesis, every candidate constrained to land on a walkable square, and a direct write-test on the `0x30`–`0x45` block that does move as you walk (it does not teleport the character). Only the clock minute moves on every step. So there is deliberately **no teleport and no "you are here" marker**, and the trainer's `docs/ReverseEngineering.md` §4.5 records what was ruled out so the next attempt starts further along. `ARCSP`*nn* (952 bytes, loaded at `DGROUP:0x7EB2`) is identified but not decoded and never touched. Game knowledge stays local (`CharacterFormat` with its `LiveFieldsLength = 0xE4` prefix that both the poll loop and the structural scan use instead of the full 12 KB, `CharacterRecord` whose setters report the exact byte range they touched through a `flush` delegate so the shell writes 1–32 bytes rather than 12 KB, `AttributeBook`, `CityBook` plus `CityMap`, which owns the drawn 64 × 64 location map — one set of geometry and colours shared by the trainer’s interactive canvas and the SVG it exports, so the two cannot drift, `PotionBook`, `GameFacts`); `CharacterViewModel` deliberately keeps **two** views of the record — editable properties bound two-way, and a separate read-only live mirror the poll loop refreshes — so a background refresh can never fight a half-typed value in a text box. `test/FormatCheck` runs 417 checks with the shipped character files present and 387 without, all with no live game: the decoded layout against a fixture built from the values confirmed on screen, assertions pinning each offset to the `DGROUP` address the game's own display template names, the locator anchors and `LooksLikeRecord` against both real and deliberately broken windows, name encode/decode/truncation/clearing, every clamp and bulk action and the exact flush range of each setter, the reference tables and the map renderer, and the view-model's edit/clamp/freeze behaviour through a fake host — plus a final group that parses the shipped `ARCCD*` files and is **skipped with a note** rather than failed when those copyrighted files are absent. Its RE notes and a play/strategy guide with maps live in its committed `docs/` (and in the game directory's own `docs/`). `AirborneRangerTrainer` (Airborne Ranger — MicroProse, 1988, IBM version 441.01) also references Common and has a **string-anchored `GameLocator`**, but the shape of the target is what matters. `AR.EXE` is **EXEPACK-compressed** — zero relocations, entry point 37 bytes from the end of the load image, `Packed file is corrupt` inside it — and unpacking it turns on one detail: EXEPACK expands **in place**, so the compressor sets the last-block flag at the point where the write cursor catches the read cursor, and the remaining prefix is stored uncompressed and is already at its final address; an implementation that stops at the flag leaves the first ~52 KB (here exactly `0xCE72` bytes) zeroed. Unpacked, the 163,888-byte image is a **medium-model** program whose entry code names its own segments (`mov ax,cs:[0]` = `0x0CE8` → `DS`, `mov ax,cs:[2]` = `0x1B51` → `SS`): code `0x00000`–`0x0CE7F`, **data `0x0CE80`–`0x1B50F` (59,024 bytes)**, stack above it. Only the load segment moves between sessions, so **every global has a constant `DGROUP` offset and there is no value scanner here at all** — if the locator fails the fix is a better anchor, not a scan. The offsets did not come from the disassembly on its own: the post-landing status panel is a **fill-in-the-blanks text template** in which numeric fields are literal `X` placeholders the game overwrites with ASCII digits, so sweeping the 52 KB code segment for the little-endian encodings of those placeholder addresses (`0xB930`, `0xB955`, `0xB97A`, …) turns up one tight cluster — the panel-fill routine at `0xBB43`, which names its own sources one field at a time (`mov al,[0xC896]` / `mov si,0xB955` / `call` the two-digit renderer). That yielded wounds `0xC892` (three is death, gated by `cmp al,3` in three separate places), rounds in the loaded magazine `0xC894` (**signed**; negative means no magazine), spare magazines `0xC895` (the panel prints this **plus one**, matching the routine's own `inc al`), grenades/LAW rockets/time bombs `0xC896`–`0xC898`, first-aid kits `0xC89A`, carried weight `0xCA42` plus a magazine-loaded flag `0xE248`, the selected weapon `0xC891` (0 carbine, 1 grenade, 2 LAW, 3 time bomb, 4 knife), and the mission tally `0xA2D4`/`0xA2D6`/`0xA2D8`. The mission clock is the field that would defeat a Cheat-Engine-style workflow entirely: it is **three separate bytes each holding one decimal digit** at `0xBE54`–`0xBE56`, so scanning all 16 MB of DOSBox RAM for the 16-bit value 600 while the panel reads `TIME 600` returns nothing but unrelated tables. Two arithmetic identities keep the table honest and are asserted in `FormatCheck`: the displayed magazine count is spare + 1, and the displayed weight is exactly the sum of the supply-pod item prices plus the loaded magazine (`3×1 + 3×2 + 1×6 + 1×3 + 1×3 + 1 = 22`). Everything was read out of a live DOSBox 0.74-3 session and matched against the screen, and spare magazines and the clock were additionally **written and watched change** (the heads-up display went to 10 magazines with the countdown running from 999). `GameLocator` sweeps for the panel caption `CARBINE MAGS` (`DGROUP:0xB923`), derives `DGROUP:0000`, and accepts a candidate only when at least two of four further literals (rank table `0xBB64`, decoration line `0xBBA6`, mission list `0xA379`, version string `0xB7F7`) also line up and the mission state behind them passes a shape check; there is deliberately **no structural fallback**, because that block is all zeros before the first mission and stale after one, so a structural sweep would return a confident wrong address. A second feature is an **offline `ROSTER.DAT` editor** in the spirit of `ColonizationTrainer`: 495 bytes = six-byte header + six 81-byte records + three-byte trailer, each record two `0D FF`-terminated text lines (rank mnemonic, 19-character name, six-digit score; then the ribbon line) followed by a ten-byte binary tail carrying the rank as an index and the decorations as a bitmask — the editor writes **both** representations, since the game reads the tail and prints the text. Field widths are pinned by the game's own blank template at `DGROUP:0x9F7E` rather than by the sample file, and the whole decode was checked against the game's *Assign a Veteran Ranger* screen. Tail bytes 3 and 4 are **round-tripped, not interpreted** (`00 00`, `01 A4`, `00 00`, `01 0F`, `02 0E`, `01 E2` across the six shipped records — correlating with neither the score nor any obvious mission count in either byte order), and a one-shot `.bak` is taken before the first save. There is **no teleport** (map position was not identified reproducibly, and the game gives you no pause in which to look for it) and **no `.DTX` decoding** (every one of the ~60 data files starts with `0x0B` and a single undecoded compression format; nothing in the trainer needs them). One trap is documented in its `AGENTS.md` and asserted in the harness: `MissionState` suppresses a write when the new value matches its shadow buffer, which is right for an edit but wrong for a **freeze** — the shadow can already hold the pinned value while the game has moved on — so `MissionViewModel.Repin` copies the game's current bytes into the shadow first. It keeps its game-knowledge layer local (`MissionFormat`, `MissionState`, `RosterFormat`/`RosterFile`, `RankBook`/`DecorationBook`/`MissionBook`/`WeaponBook`/`GameFacts`); `FormatCheck` runs 439 checks with no game present and 453 with a copy of the copyrighted `ROSTER.DAT` in `.game\` — offsets pinned to the `DGROUP` addresses the panel routine names, the two arithmetic identities, the clock round-tripping across its whole range, the locator driven over a synthetic address space (anchor split across a 1 MiB chunk seam at eleven points, exactly `MinValidators` accepted and one fewer rejected, implausible state rejected, unreadable page salvaged, no underflow near address zero, cancellation honoured), strict roster parsing and byte-for-byte round-trip, and the view-model's freeze/clamp/failed-write behaviour through a fake host. Its RE notes and a play/strategy guide live in its committed `docs/` (and in the game directory's own `docs/`). The remaining trainers are still self-contained. So a fix to the shared plumbing lands once for all of them; a fix in one trainer's local copy of the old code still needs porting.

Dot-prefixed dirs (`.docs/` teardown & strategy notes, `.data/` RAM dumps, `.game/` copyrighted assets) are **git-ignored** (`.gitignore` `.*/`) — never commit them.

## Build, Test, and Development Commands

- Root launcher: from the repo root run `.\Run.ps1` for an interactive menu of every trainer, or `.\Run.ps1 -Trainer <name|number>` to pick one directly (`-List` prints the menu and exits). It discovers any top-level folder that contains its own `Run.ps1` and forwards the shared options below to it.
- Per-trainer: `.\Run.ps1` inside each trainer folder (including `KeefTrainer`, which now has one). Restores, builds Release, and launches; a UAC prompt appears because the app manifests request admin for `Read/WriteProcessMemory`.
- Every `Run.ps1` (root and per-trainer) exposes the **same** options: `-Configuration Debug|Release` (default Release), `-Clean` (remove bin/obj first), `-NoBuild` (skip build, launch the existing exe), `-NoRun` (build only), `-Test` (run the verification harness; warns if the trainer has none), and `-Publish` (single self-contained win-x64 exe, skips launch).
- Direct: `dotnet build <project>.csproj -c Release` / `dotnet run --project <test-project>`.

## Coding Style & Naming Conventions

C# targeting `net8.0-windows` or `net9.0-windows`, **x64**, with `Nullable` and `ImplicitUsings` enabled. No `.editorconfig`, linter, or formatter is committed — match the surrounding file: 4-space indent, file-scoped namespaces, `sealed` classes, PascalCase members, `_camelCase` fields, `const` hex for offsets, and XML `///` docs on public members. Keep reverse-engineered constants in the game layer; follow the read-validate-write pattern so a shifted layout is never corrupted.

## Testing Guidelines

There is no xUnit/NUnit suite. Trainers that have one use a headless console harness — usually `FormatCheck` (`net8.0` or `net8.0-windows`), or `Verify` in `SwordOfTheSamuraiTrainer` — that asserts parsers against captured dumps/save files and exits 0 (pass) or 1 (fail). The GUI cannot be smoke-tested headlessly — it needs an interactive desktop and a running game. Keep the harness green.

## Commit & Pull Request Guidelines

The root repository has no commit history yet. Per the sibling projects, write imperative, sentence-case subjects (join related changes with a semicolon); describe which game state a change reads/writes and how it was confirmed against the live game.
