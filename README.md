# Game Trainers

A collection of independent, Windows-only **live-memory trainers** for classic games — mostly DOS titles running under **DOSBox / DOSBox-X**, plus five native 32-bit Windows titles (`ImperialismIITrainer`, `BeachHead2000Trainer`, `Civilization3ConquestsTrainer`, `LegendOfGrimrock1Trainer` and `TheQuestTrainer`, which attach straight to the game process). Each trainer is a small C#/WPF app that attaches to the running process, signature-scans (or value-scans) its RAM to locate the game's state at runtime (addresses are discovered live, never hard-coded), and reads/writes it while you play — freeze toggles, "max" buttons, teleporting, and, for some titles, offline save editing. Several trainers also include a reverse-engineering workspace documenting how their offsets were recovered.

Each game lives in its own self-contained folder with its own solution/project, `README.md`, run script, and (for most) an `AGENTS.md` contributor guide.

### Shared library

`GameTrainers.Common/` is a small shared library holding the game-agnostic plumbing that used to be copied between trainers: the process/guest-memory access layer (`GameTrainers.Common.Memory`) and the hand-rolled MVVM base types (`GameTrainers.Common.Mvvm`). The MM1-family trainers — `MightAndMagic1Trainer`, `BardsTale1Trainer`, and `PoolOfRadianceTrainer` — reference it instead of duplicating that code, as do `DragonWarsTrainer`, `MinesOfTitanTrainer`, `WarOfTheLanceTrainer`, `ThePerfectGeneral2Trainer`, `BattleTech1Trainer`, `QuestForGlory1Trainer`, `DarklandsTrainer`, `DarkDesigns1Trainer`, `WastelandTrainer`, `MoriaTrainer`, `ColonizationTrainer`, `RailroadTycoonTrainer`, `ImperialismIITrainer`, `AmberstarTrainer`, `BeachHead2000Trainer`, `AlternateRealityTrainer`, `HillsfarTrainer`, `EyeOfTheBeholder1Trainer`, `JumpmanLivesTrainer`, `Wizardry1Trainer`, `Civilization3ConquestsTrainer`, `LegendOfGrimrock1Trainer`, and `TheQuestTrainer`; each keeps only its own game-specific locators and scanners. `WastelandTrainer` locates the party by **structure** (an array of seven contiguous 256-byte records that pack from slot 0) rather than by a static anchor, and teleports by writing the party's X/Y into the party-state header that precedes the roster. `ThePerfectGeneral2Trainer`, `BattleTech1Trainer`, `QuestForGlory1Trainer`, `DarklandsTrainer`, `MoriaTrainer`, and `BeachHead2000Trainer` drive Common's `MemorySearcher` as a Cheat-Engine-style value scanner rather than a fixed locator, because their live game state has no stable static signature to anchor to (`BattleTech1Trainer` additionally uses Common's `BytePatternScanner` to *detect* the game via its read-only EXE strings; `QuestForGlory1Trainer` additionally exposes a Day/Time editor and a Teleport editor that write directly to SCI0 global variables once their addresses are scanned and pinned; `DarklandsTrainer` targets a PKLITE-packed, extender-relocated EXE that has no reliable detection signature either, so it has neither a locator nor a detector and keeps only its Confirmed attribute/skill/currency/Fame reference tables and a read-only DEFAULT-save reader; `MoriaTrainer` targets UMoria 5.5.2, a DJGPP-compiled 32-bit DPMI roguelike whose heap address changes every session, so it has neither a locator nor a detector — it uses `MemorySearcher` with 14 guided scans for character stats plus a relative-scan teleport that locates `char_row`/`char_col` by walking cardinal directions in-game, and keeps its Confirmed game-knowledge layer local — the stat encoding, the cave cell constants, a curated monster roster including the Balrog, the 31+31 spells, the item categories, and the 51-level descent reference). `ColonizationTrainer` (Sid Meier's Colonization — MicroProse, 1994) is the odd one whose **primary** feature is an **offline save-game editor** rather than a live trainer: the `COLONYxx.SAV` format is a flat little-endian serialization with a `"COLONIZE"` signature and no checksum, so it edits any power's gold/tax/Founding-Fathers and any colony's stockpile in place (the human player's gold is a 4-byte field at a nation-record offset computed from the header's colony/unit counts, verified byte-for-byte against the shipped saves); it also offers Common's `MemorySearcher` as a live value scanner for gold/tax/bells, and keeps its own `SaveFormat`/record views and game-knowledge books local. `ImperialismIITrainer` (Imperialism II — Frog City / SSI, 1999) is the repo's only **native 32-bit Windows** target: it attaches straight to `Imperialism II.exe` (no emulator). Its primary path is a **one-click auto-locate** — because the exe has a fixed image base and no ASLR, a static global always points to the player's nation object, so a `GameLocator` follows it and pins the treasury (`+0x130`) and warehouse resources (`+0xDD4`) with no scanning; Common's `MemorySearcher` (guided Treasury/Resource/Labour scans) is the build-independent fallback. It has **no save editor** (the `.imp` save has no matching map). The anchor was recovered by live RE — the game's own linker map names the data model (`TGreatPower : TCountry`, treasury a 32-bit `long`, stockpiles 16-bit) but is an earlier build than the shipped exe, so the map's *addresses* were re-recovered with a pointer scan. It keeps its `GameLocator`/`NationLayout` and `CommodityBook` (the 28 Age-of-Exploration goods from the game manual, ten confirmed by reading the live warehouse) local. `RailroadTycoonTrainer` (Sid Meier's Railroad Tycoon — MicroProse, 1990) is a DOS-under-DOSBox target that, like the MM1-family trainers, **has a string-anchored `GameLocator`**: Railroad Tycoon is an almost-entirely-static Microsoft-C build, so the player's cash is a signed 16-bit word (in units of $1,000) at a fixed offset in its data segment (DGROUP). The locator finds DGROUP by two static report labels the game always keeps in memory (`"Outstanding Loans: "`, `"Stockholders Equity: "`), validates with the year global, and reads cash at its known offset — one-click auto-locate that pins cash and year with no scan (live-confirmed against the running game), with `MemorySearcher` as the build-independent fallback. There is **no save editor**: the `.SVE` is a variable-length, count-keyed serialization in which cash is not a discrete field. It keeps its `RtLayout`/`GameLocator` and its `LocomotiveBook`/`GameFacts` reference tables (the engine rosters double as the startup copy-protection quiz answer key) local. `AmberstarTrainer` (Amberstar — Thalion Software, 1992) also references Common and follows the structural-scan model: Amberstar was originally developed for the Atari ST (Motorola 68000, **big-endian**) and ported to PC, so all multi-byte values in its 1146-byte character records are big-endian. The party is up to six contiguous records (each validated by its `00 FF` magic header, type = Person, plausible fields, and an ASCII name); the roster address changes every DOSBox session, so `PartyLocator` scans every readable region for a window matching the party shape exactly — no static anchor. It keeps its game-knowledge layer local (`CharacterFormat` offset table, `CharacterRecord` big-endian view, `SpellBook`/`RaceBook`/`ClassBook` = 96 spells, 7 races, 8 classes). The `PARTYDAT.SAV` save file uses an unknown compression method and is not editable; this trainer edits live memory only. Its RE notes and strategy guide live in its committed `docs/`. `BeachHead2000Trainer` (BeachHead 2000 — Digital Fusion / WizardWorks, 2000) is the repo's **second native 32-bit Windows** target: it attaches straight to `Bh.exe` (shipped in the Steam "BeachHead Gold Edition" package) — no emulator. Its mutable state (health, ammo, score, current level) is heap-allocated with no stable static anchor, so it has neither a locator nor a detector and uses `MemorySearcher` with six guided scans (all Int32). It additionally exposes a **level-file editor** for the shipped `Level_00`…`Level_60` plain-text scripts (starting ammo, time limit, enemy aggression, artillery flag), which `LevelFile` parses and round-trips without losing comments or unknown lines. It keeps its Confirmed game-knowledge local (`GameFacts` constants, `WeaponInfo`/`EnemyInfo`/`ControlInfo` reference tables). `SwordOfAragonTrainer` (Sword of Aragon — SSI, 1989) also references Common and is, like `ColonizationTrainer`, primarily an **offline save editor**: Sword of Aragon is a compiled **QuickBASIC 3.0** DOS game linked against the absent **BRUN30** run-time module, so its code stream is a sequence of far calls into a module that is not in the image and **does not disassemble** (a full Ghidra auto-analysis of `SWORD.EXE` recovered ~350 instructions from a 40 KB image, with no cross-references to any interesting string) — which means no variable address is statically recoverable, but the *data* is almost entirely legible. `ARAGON.HS?` is plain CSV (a 3-line header whose third line carries wealth/score/income/upkeep, then 20 city blocks of 14 lines each, then a 2-line trailer) and `ARAGON.HR?` is an array of exactly 80 fixed 100-byte roster records split 20 characters + 60 units, so both are edited field-by-field in place with everything else round-tripped verbatim and a one-shot `.bak` taken before the first write. The roster layout was proved arithmetically rather than guessed: summing the unit/equipment price tables that `SWORD.EXE` carries as QuickBASIC `DATA` text reproduces each record's stored make/train/upkeep and stacking-size fields for **623 of 623** occupied records across the 15 shipped saves and 16 (player class, unit type) pairs — including the class purchase discounts (Warrior halves Infantry; Knight takes 25 % off Cavalry *and* Mounted Infantry, which the rule book does not mention; Ranger takes 25 % off Bowmen and Horse Bowmen). Its live tab has **no `GameLocator`** in the usual sense but is not a blind value scanner either: QuickBASIC stores every string literal behind a 4-byte `(length, DS-offset)` descriptor and the whole literal pool sits at one constant offset from the file image, so `DgroupLocator` signature-scans DOSBox for a distinctive 38-byte `ARAGON.EXE` literal whose `DS:` offset is known, accepts the hit only when at least two of three further literals also line up at their own expected offsets (a three-of-four match at minimum, with the count reported), derives `DS:0000` from it, and searches that single 64 KiB segment — with Common's `MemorySearcher` as the build-independent fallback. Gold is **Microsoft Binary Format**, not IEEE 754 (QuickBASIC 3.0 predates Microsoft's move to IEEE), so it is scanned and written through a local `Mbf` converter; usefully, positive MBF singles stay monotonic read as unsigned Int32, which is what makes Increased/Decreased narrowing work on gold at all. The startup copy protection ("using the Sword of Aragon poster… enter the first word of the summary information for that city") is answered rather than patched: the complete 13-city × 4-field answer key is stored as plain literals in `SWORD.EXE` and ships in the trainer's `ProtectionBook`, so no game executable is modified. It keeps its game-knowledge layer local (`GameFacts`, `Mbf`, `UnitBook`, `RosterFormat`/`RosterRecord`/`RosterFile`, `CsvRow`/`CityRecord`/`KingdomFile`, `SaveSet`/`SaveBackup`, `CityBook`/`SpellBook`/`ProtectionBook`/`TerrainBook`), and its `FormatCheck` harness runs 457 checks (272 without the copyrighted saves) — MBF round-trips, the cost model, the documented hard limits pinned to literals, table invariants, synthetic roster/kingdom fixtures, and every shipped save parsed and round-tripped byte-for-byte. Its RE notes and a play/strategy guide with maps live in its committed `docs/`. `ARAGON.HT?` (the world grid) is deliberately neither read nor written. `PiratesTrainer` (Sid Meier's Pirates! — MicroProse, 1987, IBM version 432.02) also references Common and, like `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`**. Its target is unusual: the shipped distribution is a DOS conversion of the original *self-booting* release, in which a 1,983-byte shim (`PIR.EXE`) opens the raw floppy images `DISK1`/`DISK2`/`DISKS` as ordinary files, hooks **INT 80h** (an `INT 13h`-style sector read/write), **INT 81h** (select disk) and **INT 82h** (a keyboard poll where scancode `0x44` = **F10** quits to DOS), and then EXECs `DISKP` — the game proper, a plain MZ image whose first 32 bytes are a relocated segment table putting `DGROUP` at image paragraph `0x1124`. Every global therefore has a constant DGROUP offset, so `GameLocator` sweeps DOSBox for the title-screen literal `"COPYRIGHT (C)  1987  MICROPROSE INC."` (DGROUP `0x0183`), derives `DGROUP:0000 = hit − 0x0183`, and accepts the candidate only if the eight-byte `"PIRATES!"` save magic (`0x4128`) and the `JAN…DEC` month table (`0x31C9`) also sit at their offsets, the era code and date decode sanely, **and** the run-time-loaded settlement table at `0x4240` parses as 24-byte records — that last check is what a buffered copy of the program image cannot fake. It then pins gold (an **unsigned** `int16` at `DGROUP:0x4847` that the game's own add-gold routine *saturates* at 65,535 rather than wrapping — fixed beyond doubt by the matched add/spend pair, the latter printing "Not enough gold."), crew, personal wealth (`0x4742`, in tens of gold), land (`0x4745`, in units of 50 acres), the flat 360-day calendar (`0x9A9F`/`0x9A9D`/`0x9A2B`) and the era code (`0x475A` — stored as 0, 2, 3, 4, 5, 6, *not* 0–5, which is what makes `1560 + 20 × code` produce the six offered years), and lists the era's settlements live so the user can eyeball that the locate is right before poking. `MemorySearcher` (guided Gold/Crew/Any-value scans) is the fallback. There is **no save editor**: the shipped `DISKS` is an unformatted blank, so the on-disk slot directory could not be validated, although the 1,940-byte in-memory save block at `DGROUP:0x4130` and its `PIRATES!` magic are both confirmed. Its `CityBook`/`FleetSchedule` are **generated** from `DISK1` (six 1,024-byte era blocks at `0x54000 + 0x400 × era`): 32 settlements in 1560 rising to 41 by 1680, each with map position, nation, forts, garrison, population and treasury, plus the Treasure Fleet / Silver Train itineraries — which double as the answer key to the 1987 manual's date-lookup copy protection. Both the routes *and* their calendar phase come out of the binary (`slot = day/15 − bias + 2 × (era & 1)`, bias 18 for the Fleet and 6 for the Train), and reconstructed that way they reproduce the shipped answer key 11 of 12 itineraries entry-for-entry. Neither protection is active in this build — the disk check cannot fire once every sector comes from a file, and the manual question is absent from the program's complete 589-record display-string table. The whole teardown was **static**; that is stated plainly in its README and RE doc, and is why the locator validates three anchors plus the settlement table. `AlternateRealityTrainer` (Alternate Reality: The City — Datasoft / Intellicreations, IBM PC conversion 1987–88) also references Common and, like `PiratesTrainer` and `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`** — but it got there by a different route. `CITY.EXE` is a plain unpacked MZ image with no symbols, and Ghidra's auto-analysis recovers only ~138 functions from 330 KB (a 1987 large-model binary whose control flow is almost entirely far calls through relocated pointers), so the **disassembly was a dead end**. What cracked it was the game's own text engine: every message is a byte-coded template in which literal text is ASCII with **tab (`0x09`) standing in for the space character**, and `0xB0`/`0xB1`/`0xB2`/`0xB3` mean "print the u32/u16/u8/string at `DGROUP:⟨operand⟩⟩`" — so the operands of the status-bar and inventory-panel templates *are* a symbol table for the game's own display variables. Sweeping for those opcodes produced the character layout mechanically, and every field was then confirmed against the running game. The character is one 12,288-byte block (written to disk verbatim as `ARCCD`*nn*) at `DGROUP:0x4EB1`, and it is the **working copy**, not a save snapshot — a live scan finds exactly one occurrence of the attribute cells in the whole 222 MiB DOSBox process. `GameLocator` sweeps for the status-bar header literal `Stats STA   CHR   STR   INT   WIS   SKL` (`DGROUP:0x012A`), derives `DGROUP:0000`, requires at least two of three further literals to line up at their own offsets **and** the record behind them to pass a structural check (printable name; seven attribute records whose current and maximum bytes sit at or below the natural maximum, which is what a Wraith-drained character actually looks like; plausible level; hit points within their maximum; a next-level threshold at or above the current experience), with a pure structural scan for that same shape as an **opt-in** fallback behind a separate "Scan anyway" button, because run automatically against the wrong process it will eventually match unrelated data — measured live at **~40 ms, 3/3 validators**. Two details bite: the record stores attributes as `STR INT WIS SKL STA CHR SPD` while the status bar prints `STA CHR STR INT WIS SKL` (and has no column for the seventh, Physical Speed), and the hunger/thirst/weariness block at `0x30`–`0x45` is rewritten by the game every tick and reverts any edit within seconds, so it is deliberately never written. There is **no save editor** — the game owns its own files and the trainer edits live memory only. The trainer also carries **the city's real street map**: scoring every 4,096-byte window in `CITY.EXE` against the 60 building squares the shipped hint file names found it at file offset `0x279F0` (loaded verbatim to `DGROUP − 0x61B0`) with a score of 92 out of a possible 95 against a runner-up of 59 (a richer metric than the run-time check, which is a plain 60-square count the real map passes at 57) — one byte per square, the low nibble a location type (1 Inn … 8 Guild, matching every known coordinate) and `0x40`/`0x20` marking a building block / a wall. `CityTerrain` reads it from the attached game or from the player's own `CITY.EXE` and **never ships it**, refusing any block that fails to explain 80 % of the known squares. **Map position, by contrast, was searched for and not found** — differencing over one-step and twenty-step walks, both coordinate-pair and map-pointer hypotheses, candidates constrained to walkable squares, a direct write-test on the one block that does move as you walk, and later a whole-16 MB pass keeping only bytes that changed on the step out and returned on the step home. That last pass is started rather than finished (a long straight walk keeps being interrupted by encounters, which block walking and turning), so there is deliberately **no teleport and no "you are here" marker** rather than an unverified write. The city does carry a second 64 × 64 plane at `DGROUP − 0x71B0` giving each square a **location ID**, which a 28-entry name table turns into `City Square`, `Gold Alley`, `North Main Street` and the rest — that is how the game composes its status line, and it is documented but not yet used by the trainer. It keeps its game-knowledge layer local (`CharacterFormat`, `CharacterRecord`, `AttributeBook`, `CityBook`, `CityTerrain`, `CityMap` — the drawn 64 × 64 map shared by the interactive canvas and the exported SVG — `PotionBook`, `GameFacts`), and `FormatCheck` runs 417 checks with no game present (387 without the copyrighted character files) — including assertions that pin each offset to the `DGROUP` address the game's display template names — plus a group over the shipped `ARCCD*` files that is skipped with a note when those copyrighted files are absent. Its RE notes and a play/strategy guide with maps live in its committed `docs/` (and in the game directory's own `docs/`). `AirborneRangerTrainer` (Airborne Ranger — MicroProse, 1988, IBM version 441.01) also references Common and, like `PiratesTrainer` and `RailroadTycoonTrainer`, **has a string-anchored `GameLocator`** — but the route to it is the interesting part. `AR.EXE` is **EXEPACK-compressed** (zero relocations, entry point 37 bytes from the end of the image, `Packed file is corrupt` inside it), and unpacking it needs one detail most implementations get wrong: EXEPACK expands *in place*, so the compressor sets the last-block flag where the write cursor catches the read cursor and the remaining prefix is stored uncompressed and already at its final address — stop there and the first ~52 KB come out zeroed. Unpacked it is a **medium-model** program (one code segment, one data segment, one stack segment), so **every global has a constant `DGROUP` offset** and no value scanning is needed at all. What actually recovered the offsets was the game's own text engine: the post-landing status panel is a **fill-in-the-blanks template** in which numeric fields are literal `X` placeholders that the game overwrites with ASCII digits, so searching the code segment for the placeholder addresses finds the single routine at `0xBB43` that fills the panel — and that routine names its own sources (`mov al,[0xC896]` → grenades, `mov si,0xB955` → the GRENADES field, and so on). That gave wounds (`0xC892`, three is death), rounds in the loaded magazine (`0xC894`, signed), spare magazines (`0xC895`, which the panel prints **plus one** for the chambered one), grenades/LAW rockets/time bombs (`0xC896`–`0xC898`), first-aid kits (`0xC89A`), carried weight (`0xCA42` plus a magazine-loaded flag at `0xE248`), the selected weapon (`0xC891`) and the merit-point tally (`0xA2D4`). The mission clock is the one that would defeat a scanner: it is **three separate bytes each holding one decimal digit** at `0xBE54`–`0xBE56`, which is why searching all 16 MB of DOSBox RAM for the 16-bit value 600 while the panel reads `TIME 600` finds nothing. Everything was confirmed live — read and matched against the screen, and the weight reconstructed exactly from the supply-pod price table (3×1 + 3×2 + 1×6 + 1×3 + 1×3 + 1 = 22) — and spare magazines and the clock were **written and watched change on screen** (10 magazines, a countdown running from 999). `GameLocator` sweeps for the panel caption `CARBINE MAGS` (`DGROUP:0xB923`) and accepts a candidate only when at least two of four further literals (the rank table, the decoration line, the mission list, the version string `441.01`) line up at their own offsets and the mission state behind them is plausible; there is deliberately **no structural fallback**, because the mission block is all zeros before the first mission and stale after one, so a structural scan would return a confident wrong answer. It additionally ships an **offline `ROSTER.DAT` editor**: 495 bytes as a six-byte header, six 81-byte records and a three-byte trailer, each record being two `0D FF`-terminated text lines plus a ten-byte binary tail that repeats the rank as an index and the decorations as a bitmask — both of which the editor writes, since the game reads one and prints the other. Two tail bytes are **round-tripped rather than interpreted** (six samples do not close them), a one-shot `.bak` is taken before the first save, and the whole decode was checked against the game's own *Assign a Veteran Ranger* screen. There is **no teleport** (map position was not identified) and no `.DTX` decoding (one undecoded compression format, and nothing needs it). It keeps its game-knowledge layer local (`MissionFormat`, `MissionState`, `RosterFormat`/`RosterFile`, `RankBook`/`DecorationBook`/`MissionBook`/`WeaponBook`/`GameFacts`), and `FormatCheck` runs 439 checks with no game present (453 with a copy of the copyrighted roster). Its RE notes and a play/strategy guide live in its committed `docs/` (and in the game directory's own `docs/`). `HillsfarTrainer` (Hillsfar — SSI / Westwood Associates, 1989, build `v1.2`) also references Common and, like `PiratesTrainer`, `RailroadTycoonTrainer` and `AirborneRangerTrainer`, **has a string-anchored `GameLocator`** and no value scanner at all. Getting there needed two decompressors rather than one: `MAIN.EXE` is **double-packed**, a **SEA-AXE** stub (12-bit big-endian-packed LZW with a 4,096-entry dictionary, code `0x100` as the reset and two of them as EOF, over a byte stream that is itself RLE-coded as `F0 <count> <byte>`) wrapping an **EXEPACK** image — so a `strings` pass or a Ghidra load of the shipped file recovers essentially nothing, because the shipped file is a 1,250-byte stub plus 145,311 bytes of compressed data. Both layers were reimplemented from the stubs' own disassembly, and each closes on an exact arithmetic identity: the outer stream length `2 × 0xFC00 + 0x3F9F` is precisely the file remainder, and the inner relocation table consumes exactly the `0x1F9A` bytes between its start and `header + exepack_size`. The EXEPACK layer sets the same trap as in `AirborneRangerTrainer` — it expands *in place*, so the unconsumed-input and unfilled-destination counts come out equal (117,144 bytes here) and that prefix must be copied across verbatim or most of the program comes out zeroed. Unpacked, it is an ordinary Microsoft C 1988 build with a **single data group at load segment + `0x277A`**, which is what makes a locator sufficient: every global has a constant `DGROUP` offset, and the entire game state that matters is **one 188-byte character record at `DGROUP:0x094C`** (the shipped image's default name, `Kerwin`, sits at `DGROUP:0x0950` — the record's name field — which confirmed the base independently). Only the load segment moves between sessions; it was measured at three different addresses across three runs, so nothing is hard-coded. `GameLocator` sweeps for the game's own 69-byte startup banner (`WARNING: DO NOT RUN MEMORY RESIDENT PROGRAMS WHILE PLAYING HILLSFAR!!`, `DGROUP:0x0D1A`) and accepts a candidate only when at least two of four further literals also line up at their own offsets **and** the record behind them passes a shape check; all five were verified to occur exactly once in a live 16 MB guest, and the locate measured **82 ms at 4/4 validators**. There is deliberately **no structural fallback**: the record has a printable name and plausible attribute bytes, a shape that will eventually match unrelated data in 16 MB of guest RAM, and a confident wrong address would turn one “Max everything” click into a write into another program's memory. A second trap is that **most of the game's text is digraph-compressed** — bytes `>= 0x80` expand to two characters via a 144-byte table at `DGROUP:0xAAA4` (`first = T[i >> 3]`, `second = T[16 + (i >> 3) * 8 + (i & 7)]`, solved against fifteen expansions recovered from words whose plaintext the class and building tables give away, and reproducing all fifteen exactly) — so `“Temple of Tempus”` does not occur anywhere in memory and every anchor must be **raw bytes sliced out of the unpacked image**, not decoded text. Applying the codec decodes 734 strings out of `DGROUP`, which is where the trainer's reference tables come from: the eighteen city locations with the game's own spelling (`Cemetary` included), the eleven legal class combinations, and the eight-opponent arena roster together with the four fighting tells the game teaches through pub gossip. The record's fields were pinned by writing sentinels into the running game and reading them back off its own screen — one pass put `ZZTOP` / `Str 17(88)` / `Int 3` / `Age 44` / `HP 77(99)` / `Gold 12345` / `Exp 54321` / `Level 9` on the character sheet simultaneously, a second `Female Elf` / `Chaotic Evil`, and a third confirmed the two HUD consumables as knock rings (`+0x86`) and healing potions (`+0x87`), both capped at 99 by the game's own purchase code. Two structures are worth naming: the **class bitmask** at `+0x35` is the single most-referenced byte in the record (45 `test byte` sites), stores the mask in **both nibbles**, and indexes the game's class-name table directly — which is how the eleven legal combinations and the illegality of every Cleric/Thief pairing were recovered — while the class *index* at `+0x24` is only a creation-menu index mapped through a 16-byte table that has no slot for Magic-User/Thief, so the mask is authoritative; and the **four class levels** at `+0xB7`–`+0xBA` (Cleric, Magic-User, Fighter, Thief, in descending mask order) carry six or seven identical `inc byte` sites each, one level-up path per class. The **clock routine was decoded in full** and gives the trainer two facts no manual states: one game hour costs **122 real seconds** (a game day is about 49 real minutes), and natural healing is exactly **`1 + clamp(Constitution − 14, 0, 5)` hit points per 24 game hours** — which is why editing the hour byte at `+0x44` is a genuinely useful feature rather than a novelty, since most of Hillsfar's eighteen buildings are shut most of the day and three never open at all. It additionally ships an **offline character-file editor**, safe because the format has nothing hidden in it: `.HIL` and `.PRE` are a **raw dump of the same 188 bytes**, with no header, no checksum and no encryption. That was closed three ways — the loaded record matched the file byte-for-byte; a near-total rewrite of the record in memory followed by the game's own *Save your current Hillsfar character* produced a file identical to the edited memory, carrying bytes `0x00`–`0x03` across unchanged (a content checksum would have had to change); and a file edited on disk loaded through the game's own menu with every value on the character sheet. Setters report the exact byte range they touched so the shell writes 1–4 bytes rather than the whole record, which matters because the record sits next to the clock and its eighteen per-hour countdown timers that the game rewrites constantly. Unknown bytes — the 32-bit counter at `+0x00`, the flag byte at `+0x45`, `+0x22` — are round-tripped, never interpreted, and the three thief-skill bytes at `+0x32` are marked Inferred. There is **no quest editing** (the twelve `Q*.BIN` scripts are identified but not decoded) and **no teleport**. It keeps its game-knowledge layer local (`CharacterFormat`, `CharacterRecord`, `CharacterFile`, `ClassBook`, `RaceBook`, `LocationBook`, `ArenaBook`, `LockPickSet`, `TextCodec`, `GameFacts`), and `FormatCheck` runs **2,058 checks with the shipped character files present and 1,991 without** — every offset pinned to the `DGROUP` address the teardown established, the clock rule at every boundary hour, the healing formula across its range, the two opening-hour ranges that wrap past midnight, the codec against all fifteen expansions plus its non-ASCII 144th byte, every clamp and flush range, and the locator driven over a synthetic address space with the anchor placed at every offset across a 1 MiB chunk seam. Its RE notes and a play/strategy guide with maps live in its committed `docs/` (and in the game directory's own `docs/`). `JumpmanLivesTrainer` (Jumpman Lives! — Apogee Software, 1991, Dave Sharpless) also references Common and has a **byte-pattern-anchored `GameLocator`**: the game is a Borland Turbo Pascal 6.0 platformer whose complete source code and Borland linker map (`JMLIVES!.MAP`) were recovered from archive.org, giving every global's DGROUP offset directly. The locator sweeps the emulator for the 22-byte `jp1` jump-trajectory table at DGROUP `0x7D46`, validates with the `PLAYSPEED` and `ftwo` patterns, and reads the 92-byte player records at `DGROUP + 0xCFE6` — one-click auto-locate, no value scanning. It edits lives, score, time bonus, level, speed, and player X/Y, with freeze toggles and a trainer-mode toggle. There is no save editor (the save is a raw dump of player records, editable live instead). Its RE notes and strategy guide live in its committed `docs/`. `DarkDesigns1Trainer` (Dark Designs I: Grelminar's Staff — Softdisk / Big Blue Disk, 1990, by John Carmack) also references Common and follows the dual-locator model: `DARKDES.EXE` is **LZEXE 0.91**-compressed (identified by the `LZ91` signature at offset `0x1C`); once unpacked (137,616 bytes, 855 relocations) it is a multi-code-segment (medium/large model) Borland C build with a single DGROUP, whose character buffer lives in BSS, so the roster address changes every DOSBox session. `RosterLocator` uses a **string-anchored primary** — the 34-byte title string `"Dark Designs I : Grelminar's Staff"` is unique in guest RAM — searching a 256 KB window forward for the 15-record character pattern, with a **structural fallback** that scans all readable memory for contiguous 72-byte records (occupied slots validated, empty slots all-zero, packed from slot 0), then a content-matched sweep for the game's party working copies so live edits survive its own save. The **72-byte** record layout (name, status, class, five uint16 LE attributes, level, uint32 experience and next-level threshold, magic current/max, body current/max, gold, four readied-equipment bytes and a ten-byte carried pack) was recovered by **disassembling** the unpacked EXE and cross-checked against the shipped `DDCHARS.DAT` (one character, "CHRISTOPHER", Fighter L1). A separate `CreationScanner` finds the town (C)reate screen's **rolled stat pool** — five contiguous uint16 LE values that are not a roster record, so `RosterLocator` cannot see them — by signature-scanning the five numbers the player types as a *multiset*, which makes the lock order-insensitive and still resolved to exactly one address in the whole emulator process in live testing. Its Create tab then taps `R` to re-roll until the set can be arranged to meet the player's per-attribute minimums, and spells that arrangement out; the pool is also writable, confirmed live (a written 18 reached the created character, though the row of numbers already painted on screen is not repainted). The dice were **measured rather than guessed** — 400 automated re-rolls off the running game gave `10 + random(5) + random(5)` per value, a 10–18 triangle with mean 14 (chi-square *p* ≈ 0.66) — which lets `RollOdds` price any target exactly by enumerating the 1,287 sorted five-value combinations, cross-checked in `FormatCheck` against brute force over all 59,049 outcomes. It additionally ships an **offline `DDCHARS.DAT` editor** (1,224 bytes = 144-byte header + 15 × 72-byte records, no checksum, one-shot `.bak`) that edits inventory and readied equipment too, and a References tab with all 16 spells (8 wizard + 8 priest), the 41 obtainable items, and 43 monsters transcribed from the EXE. A **Maps tab** draws Grelminar's five castle levels, tracks the party live and teleports it: each level is a 12,648-byte `DDMAP<n>.DAT` the game reads *verbatim* into one buffer at `DGROUP:0x50F4`, laid out as a 32×32×4 wall grid indexed `x*128 + y*4 + facing`, a 32×32 contents array (bit 7 = mapped, bits 0–5 = event code) and 127 forty-byte description lines — so the level's own room names (`MAIN GATE`, `GRELMINARS STAFF ROOM`) are read out of the map rather than curated. `MapLocator` derives the party position (four `uint16` at `DGROUP:0x1320`, the same words the save header carries at offset `0x08`) from the already-located roster and validates it against **wall reciprocity** (a square's east wall byte equals its eastern neighbour's west wall byte, 3,968 of 3,968 interior pairs on every shipped level) plus **text-table consistency**, which pins the byte alignment that reciprocity cannot — reciprocity relates squares a fixed distance apart, so it survives sliding the grid by whole squares, and 113 shifted offsets passed it in a live measurement. A structural sweep for the same signature is the fallback. Live it located in **1 ms** and read a buffer differing from `DDMAP3.DAT` on disk by 2 content bytes and 0 wall bytes. The live teleport writes **X, Y and facing only, never the level** (the game loads a level's map when it takes a stairway, so moving the level alone would strand the party on the wrong map); changing level is the save editor's job, where the game reloads the matching map itself. Its RE notes and a strategy guide with full ASCII maps of all five levels live in its committed `docs/`. `LegendOfGrimrock1Trainer` (Legend of Grimrock — Almost Human, 2012; this build is the Steam release, version 1.3.7, PE-timestamped 2013-02-08) is the repo's **fourth native 32-bit Windows** target and the one where the usual approach does not apply at all: the exe is a C++ engine wrapped around a statically linked **LuaJIT 2.0.0-beta9** (it exports the entire Lua C API, including `luaJIT_version_2_0_0_beta9`), and the whole gameplay model lives in ordinary Lua tables — searching the 1.8 MB image for `health`, `champion` or `strength` returns *nothing*, while the live `_G` holds `party`, `dungeon`, `gameMode` and 149 loaded `.lua` chunks. So there are no game offsets to maintain: a champion's health is `party.champions[i].stats.health.value`, and the trainer reads LuaJIT's own object model (`TValue`, `GCstr`, `GCtab`, `Node`, `lua_State` — 32-bit, `LJ_GC64` off) to walk there by name. Locating the VM is two chains: the module's single static `lua_State *` at RVA `0x00188AB8` (Ghidra shows exactly one xref to it, a WRITE inside the C-API registration function whose caller also calls `luaL_newstate`), and, when that is stale or a rebuild moved it, a sweep for LuaJIT's `GG_State` signature — a thread object whose `glref` equals its own address plus `sizeof(lua_State)`, which is true of the main thread and of no coroutine. ## Prerequisites

- **Windows** (the trainers use WPF and the Win32 process-memory APIs).
- **.NET 8 SDK** (some trainers target .NET 9 — install the .NET 9 SDK to build everything).
- **DOSBox** or **DOSBox-X** running the target game.
- Administrator rights: most trainers ship a manifest that requests elevation for `ReadProcessMemory` / `WriteProcessMemory`, so launching triggers a UAC prompt.

## Building and Running

Every trainer has its own `.\Run.ps1`, and they all expose the **same** options. Run one from
inside its folder, or use the **root launcher** to pick one interactively.

### Root launcher

From the repository root, `.\Run.ps1` discovers every trainer (any top-level folder that has its
own `Run.ps1`) and forwards the shared options to the one you choose:

```powershell
.\Run.ps1                         # menu: pick a trainer, then build and launch
.\Run.ps1 -List                   # list the trainers and exit
.\Run.ps1 -Trainer Shogun         # run a trainer by name (exact or unique partial)
.\Run.ps1 -Trainer 4 -Clean       # run the 4th listed trainer, cleaning first
```

### Per-trainer

```powershell
cd PoolOfRadianceTrainer
.\Run.ps1                         # restore, build Release, and launch (UAC prompt)
.\Run.ps1 -Configuration Debug    # debug build
.\Run.ps1 -Clean                  # wipe bin/obj first, then build and launch
.\Run.ps1 -NoBuild                # skip the build, launch the existing exe
.\Run.ps1 -NoRun                  # build only; print the exe path
.\Run.ps1 -Test -NoRun            # run the verification harness, no GUI
.\Run.ps1 -Publish                # publish a self-contained win-x64 exe, no launch
```

Shared options (identical for the root launcher and every trainer):

- **`-Configuration Debug|Release`** — build configuration (default `Release`).
- **`-Clean`** — remove `bin`/`obj` before building.
- **`-NoBuild`** — skip building and launch the most recent build.
- **`-NoRun`** — build only; do not launch.
- **`-Test`** — run the trainer's verification harness (warns if it has none).
- **`-Publish`** — publish a single self-contained win-x64 exe; skips launch.

Only `AirborneRangerTrainer`, `AlternateRealityTrainer`, `AmberstarTrainer`, `BardsTale1Trainer`, `BattleTech1Trainer`, `BeachHead2000Trainer`, `Civilization3ConquestsTrainer`, `ColonizationTrainer`, `DarkDesigns1Trainer`, `DarklandsTrainer`, `DragonWarsTrainer`, `EyeOfTheBeholder1Trainer`,
`HillsfarTrainer`, `ImperialismIITrainer`, `JumpmanLivesTrainer`, `LegendOfGrimrock1Trainer`, `MightAndMagic1Trainer`, `MinesOfTitanTrainer`, `MoriaTrainer`, `PiratesTrainer`, `PoolOfRadianceTrainer`,
`RailroadTycoonTrainer`, `SwordOfAragonTrainer`, `SwordOfTheSamuraiTrainer`, `ThePerfectGeneral2Trainer`, `TheQuestTrainer`, `WarOfTheLanceTrainer`, `WastelandTrainer`, and
`Wizardry1Trainer` ship a verification harness; `-Test` warns and is ignored on the others (including `QuestForGlory1Trainer`). `SwordOfTheSamuraiTrainer` also has `.\Edit-SotsSave.ps1` for offline save editing.

You can always build directly with the SDK:

```powershell
dotnet build <project>.csproj -c Release
```

Then start the target game — in DOSBox / DOSBox-X for the DOS titles, or directly for the five native
Win32 ones — and use **Attach** in the trainer.

## Testing

There is no unit-test suite. Trainers that ship verification use a headless console harness (usually `FormatCheck`, or `Verify` in `SwordOfTheSamuraiTrainer`) that checks the parsers against captured memory dumps / save files and exits `0` (pass) or `1` (fail). Run it via `.\Run.ps1 -Test -NoRun` where available, or `dotnet run --project <test-project>`. The GUI itself cannot be tested headlessly — it needs an interactive desktop and a running game.

## Notes

These are single-player cheat tools for the user's own saved games. They do not touch the network or any external service. Game assets are copyrighted and are **not** included — supply your own legally obtained copy. Original game files, memory dumps, and reverse-engineering notes live in dot-prefixed folders (`.game/`, `.data/`, `.docs/`) that are git-ignored.
